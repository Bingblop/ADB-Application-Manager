Android keeps hundreds of small settings that its own Settings app never shows. This tab lists them, lets you read any one, change it, add your own or delete it, and puts the old value back when you change your mind.

Where to find it: the tab named Hidden Settings ("Hidden" on the bottom bar, two lines on the tab bar: Hidden and Settings), right after Live Logcat and right before the Extra Settings tab in the default order (RRO/Monet Customization comes after Extra Settings). If it is missing, it has been switched off: see Turning tabs on and off and moving them.

Looking for Private DNS? It is not in this tab, which edits Android's own settings tables. It is in the Extra Settings tab next to this one: a small note at the top of this tab has a button that opens it.

Before you start

  • You need a working mode. The app reads and changes these settings by running Android's own settings command through your working mode (ADB over TCP, Wireless Debugging, Shizuku or Root; see Working modes and the glossary). In Read-Only mode the tab cannot even show the list. With no mode ready, a card says Needs ADB, Wireless Debugging, Shizuku or Root and its Set Up button opens Working Modes. Connect one, come back, and the list loads.
  • No computer is needed, and the tab does not use the app's own "Write Secure Settings" permission (see App permissions). What you can change is decided by the mode and by Android.
  • Which settings exist depends on your Android version and phone maker. One your phone does not have is not in the list.
Risky. These are the settings Android reads while it runs. A wrong value can cut the connection this app uses, lock you out of the keyboard or screen, or upset the system. The app marks the worst ones careful and asks first, but others can also cause trouble. If you do not know what a setting does, leave it alone. Before you change one, tap its row and use Copy value to keep the original in a note. Every change you make can be put back (see Undoing settings changes), but a lock-out can stop you reaching the app, so read "If you lose the connection" below first.

The three tables

A setting is a name with a value, such as screen_off_timeout with 60000. Android keeps them in three groups called tables, and the tab has one sub-tab for each.

TableWhat lives thereExamples
GlobalSettings for the whole phone.adb_enabled, airplane_mode_on, window_animation_scale, device_name
SecureSettings of the current user that only the system, or the shell, may change: keyboards, accessibility, location mode.default_input_method, location_mode, ui_night_mode
SystemThe classic per-user settings: brightness, screen timeout, text size, rotation, volumes.screen_off_timeout, font_scale, volume_music

Android reads many settings only at certain moments, and some phone makers overwrite a few with their own, so a change that "does nothing" is not always a fault.

What the screen shows

  • Global, Secure, System (three wide buttons) choose the table. The number under each name is its count of settings: an ellipsis while loading, an exclamation mark if it could not be read, and "matches / total" while a search or filter is on.
  • Search settings... (the box, with an x to clear it), ＋ (create a setting) and ⋯ (More: sort order, reload, your changes, copy and share).
  • Four chips: All; Switches (values such as 1 or 0, true or false, on or off, yes or no); Described (every setting the app can describe: about 1,100 of Android's own; see "What a setting does and what its values mean" below); Edited (the ones you changed with this app).
  • A status line: the count, the time it was read, and a Refresh link.
  • The list. Each row has the name, what the setting does and which values it takes when the app knows them, and the value (long values are cut after two lines). A dot after the name means you changed it. An orange edge and the word "careful" mark a risky one. (empty) means nothing is stored, (blank) only spaces. A switch at the right means the value is switch-like. The list shows 120 rows at a time; more load as you scroll or with Show more.

What a setting does and what its values mean

Under the name of each setting the list says what it does, and below that Values: which values it takes. The value the setting holds now is in bold in that line, so Values: 0 = off; 1 = priority interruptions only; 2 = total silence; 3 = alarms only tells you at a glance that Do Not Disturb is off. Tap a row and the sheet has an About box with the same, one value to a line, and a Now: line that follows what you type (type 2 and it says Now: 2 = total silence).

  • Where the text comes from. The app knows what about 1,100 of Android's own settings do (the Global, Secure and System tables of Android's source code). The ones people meet most often have been written out in plain words; the others carry the short text from Android's documentation.
  • Reading the values. 0 = off; 1 = on is a switch. A time is in milliseconds (1000 is one second, 60000 one minute). A decimal such as 1.0 is a scale: 1.0 normal, 0.5 half, 2.0 double. percent, Hz (refresh rate) and kelvin (colour warmth) are units. A list uses , or : between its items; package/class is an app component.
  • Only real switches flip. A setting the app knows takes more than 0 and 1 (for example wifi_on, zen_mode) is never flipped by a press and hold: tap it and pick one of its values.
  • The search also looks in the values text, so milliseconds or total silence finds settings.
  • A setting without a description. Phone makers and apps add many settings of their own (a name starting sec_ often comes from Samsung, miui_ from Xiaomi, a name like com.example.app.key from that app). For these the editor says What it probably is and guesses from the name and the value: an on/off switch, a time in milliseconds, a web address, a package name. It is only a guess; if you cannot tell what a setting does, leave it alone.
  • The How to read this list link under the title of the tab opens a short explanation of the three tables, a row and the kinds of value. The ? next to the title opens this guide topic.

Find a setting

  1. Open Hidden Settings. Grey bars show while the tables are read; then each button shows its count.
  2. Tap a table, or just search: the counts on all three buttons change to "matches / total".
  3. Type in the search box. It looks in the name, the value and the description, ignores capitals, and every word you type must match. timeout finds screen_off_timeout.
  4. Narrow the list with a chip, or tap ⋯ and choose Sort by: Name A-Z (default), Name Z-A or Value.

What you will see: the list shrinks to the matches, with the matching letters highlighted. If nothing matches, the page says Nothing matches "text" in Global. and offers Create "text" in Global (only when what you typed is one word that can be a setting name) and Show everything. Back clears the search first. The table, filter and sort order you used last are remembered; the search text is not.

Read a value

The value is on the row. To see all of it, tap the row: a sheet opens with the value in a box. The app also asks the phone for the real value while it opens, because the list may be a little old; if it differs, the box is updated and a message says Showing the value the phone holds now. The sheet's Reload link does the same on demand.

Change a value

  1. Tap the row. A sheet slides up with the name, the table, the description and, for a risky setting, an orange box explaining the danger. Read it.
  2. Type in the Value box, or tap a quick value. If the setting is documented, its own values come first, each with its meaning (for example 2 · total silence); then 0, 1, true, false, null, (empty), -1. A line under the box says what kind of value it looks like and what it was before.
  3. A red line means it cannot be saved yet. The limits are 20,000 characters, no control characters (invisible special codes, apart from a tab or a line break), and a size that fits in one command sent through ADB (about 62,000 bytes once quoted). Save stays grey until the problem is gone.
  4. Tap Save. For a careful setting your phone first asks you to confirm.

What you will see: the sheet stays open while the phone applies the change, so a refusal never loses what you typed. On success it closes, the row shows the new value with a dot, and an Undo bar appears for 3 seconds. Saving the same value says No change. The word null is stored as that text; use (empty) for nothing and Delete to remove the setting. The sheet's other links: Web search (looks the setting up on the web by its table and name), Ask agent (asks your Default Ask Agent what the setting is and whether it is safe to change; the setting's name, table and current value are sent to that agent's company, only when you tap the button, and many settings belong to the phone maker, so the answer may be a careful guess; until the agent has its key, or with No default chosen, the built-in web lookup answers instead), Copy name, Copy value and Copy command (the exact settings put line, to paste in the ADB Shell of the Console tab).

Flip a switch

  1. Tap the switch at the end of a row, or press and hold the row for about half a second (you feel a short tap).
  2. Confirm if it is a careful setting.
  3. The switch moves and the Undo bar says, for example, show_touches: 0 → 1.

Capitals are kept (True becomes False). Settings that look like switches but are really a choice among several values, such as zen_mode, ui_night_mode or screen_off_timeout, have no switch (holding one says Not a switch: tap it to edit). In the editor, a switch-like setting has a Flip button that only changes the box; you still tap Save.

Add a new setting

Android uses a setting only if something reads it by that exact name, so an invented one does nothing. Add settings you have a real name for, from a guide or an app's documentation.

  1. Tap ＋. A sheet titled New setting opens.
  2. Choose Global, Secure or System (it starts on the table you were in).
  3. Type the Name: up to 256 characters, not starting with a dash, with no equals sign, spaces or control characters. A red line says what is wrong.
  4. Type the Value, or leave it empty to create the setting with nothing in it.
  5. Tap ＋ Create. If the name exists, the button reads Replace, a note shows the current value, and you must confirm. The app asks the phone first, so a name missing from an old list is still caught.

What you will see: the list jumps to that table with the name in the search box, and the Undo bar says "＋ Created name". Undo deletes it again.

Delete a setting

  1. Tap the row, then Delete (red, at the bottom of the sheet).
  2. Confirm. The box says Android and apps then behave as if it was never set.
  3. The row disappears and the Undo bar says "Deleted name". Undo brings it back with its old value.

If you lose the connection

If you switched off adb_enabled or adb_wifi_enabled (or Wi-Fi, or switched on airplane mode) while the app was using ADB, the app can no longer reach the phone to change them back. Open your phone's own Settings, go to Developer options (a hidden part of Android's Settings; if you cannot find it, search the Settings for its name), switch USB debugging or Wireless debugging back on (and Wi-Fi), then reconnect in Working Modes. If another mode (Shizuku or Root) still works, Revert the entry in Changes instead. If a keyboard or accessibility setting locks you out, use your phone's own Settings to choose a working keyboard and switch accessibility services back, then revert the entry.

Hidden Settings keeps two ways back: an Undo bar that appears right after a change, and a history called Changes that keeps your last 100 changes, between launches, so each one can be reviewed and reverted later.

Where to find it: the Undo bar appears at the bottom of the screen in the Hidden Settings and RRO/Monet Customization tabs. The history opens from the clock button next to the search box of Hidden Settings, or from the Changes button under ⋯.

Before you start

  • Putting a value back is a change like any other, so it needs a working mode (see Working modes).
  • The history only knows about changes made with this app. If another app, Android itself or a computer changed a setting, it is not listed, and the app cannot tell you what the old value was.
  • The page has no backup and no restore for settings. There is no button that saves a whole table to a file or loads one back. The history is the safety net, and the section "Keep your own copy" below shows a manual way to save a list before you experiment.

The Changes history

  1. Open Hidden Settings and tap the clock button next to the search box (or tap ⋯, then Changes).
  2. A sheet titled Changes opens, with the line "The last 100 changes made with this app, newest first, kept between launches. Revert puts the old value back."
  3. Each entry shows the setting name, the table, how long ago and the date and time (for example "Global · 3 min ago · 15 Oct, 21:30"), and the change as old value → new value. A value that was not there before shows as (not set); an empty one as (empty).
  4. Tap Revert under the entry you want to undo.

When a 101st change is made, the oldest entry is dropped. If nothing has been changed yet, the sheet says Nothing was changed with this app yet. The same history is behind the Edited filter chip and the small dot after the name of every changed setting in the list.

Revert one change

  1. In Changes, find the entry and tap Revert.
  2. If the setting has changed again since (by you, by Android, or by another app), a box says name has changed since: it is now ... (this change left it ...). Put the old value back anyway? Choose OK only if you want the old value back regardless.
  3. If the setting is marked careful, you are asked to confirm once more (see Hidden Settings).
  4. The sheet closes and a message says Put back: name (or Removed: name when the entry was a setting you created, so there is nothing to put back).

Reverting is recorded as a new change, so it appears at the top of the history and can itself be reverted.

If the old value was longer than 2,000 characters, the entry shows (too long to keep) in its place and has no Revert button, because the old text was not stored. For those, use the Undo bar right after the change, or fix the setting by hand.

Revert many changes

There is no "revert all" button. Revert the entries one at a time, starting from the top (the newest), so that every entry finds the setting in the state it left it. Going out of order is allowed, but you will get the "has changed since" question for entries that depend on a later one.

  1. Open ⋯ → Changes.
  2. Tap Revert on the first (newest) entry. The sheet closes after each revert.
  3. Open ⋯ → Changes again and repeat. Check your phone from time to time, so you stop as soon as it behaves normally.

What is kept, and where

  • The last 150 changes. Older ones are forgotten as new ones arrive.
  • Where: inside this app's own storage on the phone. The app does not write a file to Downloads or anywhere else, and nothing is sent to anyone. The history survives closing the app and restarting the phone. Because it lives in the app's own storage, clearing the app's data or uninstalling the app removes it (and with it your way back).
  • Theme changes too. A Material You theme change made in the RRO/Monet tab is a change of the secure setting theme_customization_overlay_packages, and is listed here with that name. Reverting it puts the old theme setting back. Overlay on/off changes are not listed in Changes, only in the Undo bar.
  • What is in each entry: the table, the name, when it happened, the old value and the new value.

Clear the history

At the bottom of the Changes sheet, Clear history asks Forget the history of changes? The settings themselves stay as they are. If you confirm, the list is emptied, the small dots and the Edited filter forget everything, and nothing on the phone changes. You cannot get the entries back, so do this only when you are happy with how the phone behaves. The button only shows while there is something to clear.

Back up the changes you made, and restore them

Under the list in the Changes sheet there are two more buttons next to Clear history.

  • Back up changes opens Android's share sheet with a small file, hidden_settings_(date).json. It holds every setting you changed with this app: the table, the name, the value it has now, and the value it had before. Save it to Drive, send it to yourself, or keep it with your other backups. Settings whose value was too long to keep are left out.
  • Restore… asks you to pick such a file. The app checks it (a name with spaces or strange characters, an unknown table or a value that is not text is left out), compares it with what the phone holds now, and asks Put N hidden settings back from the backup?, naming the first few and saying how many are marked risky. Settings that already match are skipped. If you agree, the values are put back one after the other (a value of removed deletes the setting), the progress is shown as Restoring 3 of 12…, and one message at the end says how many worked and which did not. Every restored setting is written to the history again, so it can be reverted.

The file only knows the settings you changed here, not the whole phone, and it is for the same kind of device: a setting that another phone does not have is created, which it may ignore. A backup is not a reset button for settings the app never touched; for those, use the copy described next. Needs a working mode, like any change.

Keep your own copy before you experiment

The history cannot restore a whole table, and it does not know settings you did not change. If you are about to try several things, save the original values first.

  1. Open Hidden Settings and choose the table (Global, Secure or System).
  2. Clear the search box and tap All, so that every setting is shown.
  3. Tap ⋯, then Copy shown (a message says Copied 340 settings or similar), and paste into a notes app. Or tap Share shown and send the text to yourself.
  4. Do the same for the other tables if you want to.

The copy is plain text with one name=value line per setting. To restore something later, find the line and set the value by hand (tap the row, type, Save), or create the setting with ＋ if it was deleted. That text cannot be read back in by the app; the file from Back up changes above can.

Careful. The lists can hold personal details, such as the device name, the Bluetooth name and address, and the Android ID. Keep the copy private. If a very long list does not go through the share sheet, narrow it with the search or a filter first.

If something goes wrong

  • Revert says it could not change the setting. A sheet shows Android's own answer, the same as for any change. Read it; see "If a change is refused or nothing happens" in Hidden Settings.
  • The history is empty but you know you changed things. The changes were made outside this app, or the app's data was cleared since. Set the values back by hand from your own copy.
  • The phone is unusable after a change and you cannot reach the app. Use your phone's own Settings (Developer options, language and input, accessibility) to undo what you can, reconnect in Working Modes, then revert the entry. See also Safety.

Where to find it: the tab named Extra Settings (two lines on the tab bar: Extra and Settings), right after Hidden Settings in the default order. The top of the tab

Where it is: the Extra Settings tab (right after Hidden Settings on the tab bar), first section, Private DNS. It is not in the Hidden Settings tab, the one that edits Android's own settings, and it is no longer a card in the gear Settings page (that page has a small pointer to it).

This section changes the phone, so applying a service needs a working mode (ADB, Wireless Debugging, Shizuku or Root). Test speed

Tap Test speed. The app tries every service in the list (and the host name typed under Another host name, if there is one) and fills in each tile as soon as its answer comes in, in any order. A bar fills the button and the line under it says Testing… 5 of 15; Stop ends the test (the answers that came in stay, the others say Not tested). Leaving the tab also stops it. Starting a new test replaces the old one.

Each tile shows the time in milliseconds in all, and under it the three parts: connect (the network connection to port 853, the closest thing to a ping), TLS (the secure handshake) and answer (one real DNS lookup over that connection). Each is the middle value of three tries; if fewer than three worked, the tile says so. A tile whose service did not work says why: Name not found, No answer on 853, Certificate error, No DNS answer or Timed out. A tile that says Couldn’t test now only means the phone had too many name lookups waiting: that says nothing against the service, so test again.

When all answers are in, the quickest working service gets a Fastest pill and a bright outline, and the line under the button says which it is (Fastest on this network). The result is a measurement from this phone's network only, at this moment; a different Wi-Fi or mobile data can give another order. Sort by speed (off by default) puts the answers in speed order, quickest first, then the services not tested, then the ones that failed; off, the list keeps its usual order.

Privacy. Your phone first looks up each service's name with the DNS it uses now (once). Then each service may receive up to three short encrypted connections, each asking for example.com. See which Doze phase the phone is in, push it through the phases to test how an app behaves when the phone sleeps, and choose a power profile.

Where it is: the Extra Settings tab, the section Doze & power governor. Reading and changing needs a working mode (ADB, Wireless Debugging, Shizuku or Root); without one the section says so and its buttons are off.

The timeline

Doze is Android's deep sleep (a glossary word: the phone stops most background work when it lies still with the screen off). The timeline shows five phases, Active, Inactive, Idle pending, Idle (deep) and Maintenance, with the phone's current phase lit and the exact state Android reports under it (for example SENSING under Idle pending). A row of small chips below shows the state of Light Doze, the lighter version that starts a few minutes after the screen goes off. Both come from dumpsys deviceidle get deep and get light, read when the tab opens and after every action; Check again reads them again.

Actions

  • Force deep Doze: puts the phone into deep Doze now (dumpsys deviceidle force-idle deep). Most apps lose background work and network until the next maintenance window; the phone still rings. It stays forced until you wake the device or the phone restarts.
  • Step to next phase: moves Doze one phase forward (dumpsys deviceidle step deep).
  • Wake device: ends a forced Doze and lets Android decide again (dumpsys deviceidle unforce).
  • Simulate motion: tells Doze the phone was picked up (dumpsys deviceidle motion); a Doze that Android entered on its own ends, a forced one does not.

Each action opens the confirm sheet with one sentence on what it does and the command; after it runs, the section reads the phase back from the phone and shows that, with the command's own words under it. A phone that refuses (for example Unable to go deep idle; not enabled) is reported as such. The Motion sensor line says what the phone's own Doze report says (whether Doze uses the sensor, whether it is listening now, the sensor's name); a phone that does not print those lines reads as state unknown. Android has no switch for that sensor, so the section does not offer one.

What root theming is here

Apply theme (see RRO/Monet Customization) writes one setting and leaves it to Android to work the colours out from it. Android lets the shell user do that, and the shell user is what ADB over TCP, Wireless Debugging and Shizuku are. The controls on this card do something else: the app writes the colours themselves into Android, as an overlay it makes on the spot (the command is cmd overlay fabricate; what an overlay is, see "Two words first" in RRO/Monet Customization). Android's overlay service takes that command from root and from nobody else. That is the whole reason for the lock: Shizuku and ADB cannot write these colours; Root can.

The overlay is registered to the shell and is called com.android.shell:aam_monet. On Android 12 and 13 each colour is an overlay of its own, com.android.shell:aam_monet_neutral1_900 and com.android.shell:aam_monet_neutral2_900. Pure black backgrounds

The first control: a row named Pure black backgrounds, its line "True black dark backgrounds, panels in a few dark greys. Light mode keeps its colors, except that its darkest text becomes pure black." (on Android 16 QPR1, QPR2 and 17: "True black dark backgrounds, panels in a few dark greys. Light mode keeps its colors."), and a switch, off until you turn it on. It is not the same thing as Pure black in dark mode in this app's own Settings: that one makes this app black (Themes and colours); this one makes the phone black.

What it changes. In dark mode, Android's own backgrounds become true black (#000000), and the panels that sit on them (such as cards, sheets and dialogs) a few dark greys lighter, so they still stand out from the background. On the Colors in use card the last square of the Neutral 1 and Neutral 2 rows (shade 900) turns black. Light mode keeps its colours, except that its darkest text becomes pure black: the two shade 900 squares belong to both modes, and Android's light theme takes its main text colour from the Neutral 1 shade 900. Every other colour the overlay names is a dark-mode one. On Android 16 QPR1, QPR2 and 17, which keep the shades of each mode under names of their own, the two shade 900 colours are written for dark mode only (system_neutral1_900_dark and system_neutral2_900_dark), so light mode keeps every colour there, its text included; as read in Android's source code (not tried on a phone), Colors in use then shows the two black squares only while the phone is in dark mode. Apps that follow Material You take it as they take any system colour; apps with their own dark colours ignore it. On Android 12 and 13 only the darkest background shade changes (those versions have no separate colours for backgrounds and panels), so you get black where Android used its darkest grey and nothing else. The notification shade and the quick settings may keep a dark grey on some versions.

The switch alone writes nothing. It only says what the next Apply theme does, and it is remembered, across restarts of the app too, until you turn it off.

Step by step

  1. Get Super User (Getting Super User). The row unlocks: the Locked button and the lock go away and a switch takes their place.
  2. Tap the switch. It turns on, and the line under the Apply theme button gains a second sentence: Also writes the pure black overlay with root.
  3. Choose the colour and style as usual, or leave them as they are. Apply theme is live even when the line says This is already what the phone uses., because the overlay is still to be written.
  4. Tap Apply theme. It reads Applying… while the app writes the theme setting and reads it back, exactly as before; then, with that in, it writes the overlay: it makes it, switches it on, reads the overlay list back and asks Android which colour it now gives for the first four entries (both, on Android 12 and 13; on Android 16 QPR1, QPR2 and 17 the ones it picks by name, see "Android 16's quarterly updates" and "Android 17" above). The button stays busy until both answers are in. The overlay is the one the card showed when you tapped: the switch, More styles and Color spec stay usable meanwhile, but a change made while the button reads Applying… only counts for the next Apply theme.
  5. Android repaints within a second or two and may restart apps. A message says Pure black overlay written, the Undo bar appears with Theme applied for the whole change (the theme and the overlay), the card now says The pure black overlay is written on this phone., and Colors in use redraws a few seconds later.

On Android 14 and newer that is one overlay with every colour in it. On Android 12 and 13 Android takes one colour per overlay, so the app writes two, one after the other, and the phone repaints for each; the Overlays half then lists two rows instead of one. With a style from More styles chosen as well, or a style's newer colours from Color spec, or a style's colours adjusted by the Intensity sliders, or with your own accents from Secondary and tertiary accents, or with Accurate shades off, the one overlay carries both, and the messages and the card's line speak of the theme overlay instead: see More styles, Color spec, Intensity, Secondary and tertiary accents and Accurate shades.

What can go wrong

  • Android repaints, and apps may restart, this one included, as with any theme change. Save your work elsewhere first. The app notices its own restart and brings you back to this tab with the Undo bar waiting (Theme changed); that Undo works like the normal one (see "How to undo" below). The app notes the overlay as possibly written just before it writes it, so this also holds when the restart comes before the phone has answered; the card then says The pure black overlay may be written on this phone. until a later answer from the phone (to Apply theme, Undo or Default) says what became of it.
  • Not everything turns black. Google apps may keep their own shade of dark grey, apps with their own dark colours ignore the overlay, and how much of the phone's own screens follow it depends on the maker; on One UI, Samsung's own apps may keep Samsung's colours (see "On One UI" above). The notification shade may keep a dark grey.
  • The colours fall back. Android's own colour engine keeps running and rewrites its colours when the wallpaper changes, when dark mode is switched, and after a restart of the system interface; after one of those the pure black may be gone although the overlay is still listed on. Tap Apply theme again. The app does nothing in the background to put it back.
  • Android refuses the colours. The app decides from what it reads back, never from the command's own words: every overlay it wrote must be listed on, and every colour it asks about must come back as the colour it sent. If an overlay is missing from the list, a message says The pure black overlay was not written and a sheet titled Could not write the pure black overlay (subtitle Monet · root overlay) shows the reason and Android's own answer. If the overlay is listed on but a colour comes back different, the overlay is written and it is its colours Android does not show: the message and the sheet's title say The pure black overlay is on, but Android shows its own colors, and the sheet shows the reason, for example Android did not take the colours, and under What Android reports for each color: one line per colour asked about. An overlay listed on is remembered either way, so that Undo and Default can switch it off.
  • No answer. If the phone has not answered within a minute, the sheet says No answer from the device (timed out) and The phone may still apply it. It is looked at again in a moment.; the overlay is remembered as possibly written (the card says The pure black overlay may be written on this phone.), so Undo, Default and Apply with the switch off still switch it off, and the list is read again shortly.
  • Super User went away in between. If the grant was taken back after the row unlocked, the sheet says Needs Super User with "Shizuku and ADB cannot write these colors; Root can. Choose Root in Working Modes, then tap Apply again." The theme setting was still written, with its own Undo.
  • The theme setting is refused first. Then the overlay is not written at all; you see the usual Theme change refused sheet.
  • The theme's own answer is lost. If the app restarts before the phone has answered for the theme setting, or the phone gives no answer for it (No answer: the theme may still change), the overlay half of that same Apply theme waits: the app keeps what you chose when you tapped, reads the theme back, and once it reads back as written, it writes the overlay as that tap would have, with the usual message (Pure black overlay written). If the theme reads back as not written, nothing is written and a message says The colors were not written. Tap Apply theme again.
  • Android 14 and newer: the colour file. On these versions the colours go through one small file that the overlay command reads: the app writes it, makes it readable to every part of Android (Android reads it as its own system user, not as root), and deletes it again at the end of the same command. Whether Android can read that file from where the app puts it is one of the things not yet tried; if the write fails for that reason, the sheet shows Android's answer.
  • The overlay stays listed. Android has no shell command that removes a fabricated overlay, so after Undo, Default or Apply with the switch off, com.android.shell:aam_monet stays in the Overlays half under Disabled (two rows on Android 12 and 13), switched off and doing nothing. The app cannot remove it.

None of this has been checked on a rooted phone yet. It was built from Android's own source code and checked in tests that imitate the phone; the first run on real hardware may find something these words do not say.

The contrast setting

From Android 14, Android's Settings have a contrast level for the system colours, and Android works its own role colours out at that level. The app does the same with the colours of a style from More styles, Color spec, Intensity, Secondary and tertiary accents or Accurate shades: it reads the phone's contrast at the moment you tap Apply theme and works the role colours (backgrounds, surfaces, accents, text and outlines) and the fixed colours out at it. The five rows of shades, and so the preview, do not depend on it, and neither does Pure black. The overlay does not follow a later change: after you change the contrast in Settings, tap Apply theme again. This holds on Android 16 QPR1, QPR2 and 17 too, where the overlay carries the colours of both modes: both are worked out at the contrast read at the tap. Nothing on the card tells you; the app does not watch the setting.

After an Android update

Next to the colours, the app remembers the build of Android they were written on (Android's build fingerprint, which names the exact build) and the version family it worked them out for (one row of "Which Android versions" above). When the phone runs another build of another family, for example after the update from Android 14's first release to one of its quarterly updates, from Android 15's first release to its first quarterly update, from 15 QPR2 to 16.0, from 16.0 to 16 QPR1, from 16 QPR1 to QPR2, or from 16 QPR2 to 17, a note under the card reads Android was updated after these colors were written. Tap Apply theme to write them for this version. A monthly update within the same family gives no note: the colours depend only on the family, so Apply theme would write the same ones again. Nothing runs by itself: tap Apply theme, and the colours are worked out again for the version the phone runs now and written, and the note goes away. The note shows only while Apply theme would write the colours: with Super User, on a version of Android where the rows are not locked, and only for a style's colours, both those written then and those Apply would write now. Pure black alone gives no note: its colours are the same on every build. Colours written by an older version of this app, which did not note the build, give no note.

The names are the same there, so an overlay written on 14.0 goes on giving every colour it holds, as read in Android's source code (not tried on a phone): the role colours are then those of 14.0, until you tap Apply theme, which writes the colours of the quarterly update the phone runs now. An update from one quarterly update to another (QPR2 to QPR3, for example) gives no note: the app works their colours out the same way. Colours written on a quarterly update by a version of the app from before it could tell the quarterly updates apart were worked out as for the first release; the app counts them so, and so the note shows once the phone runs another build after that (its next update), not before. To have the quarterly updates' colours at once, tap Apply theme.

From Android 15's first release to its quarterly updates. From Android 16.0 to its quarterly updates. An overlay written on 16.0 names the plain shade names (system_accent1_500 and the rest), one colour each. What each slider does

Each slider goes from 0% to 200% in steps of 5%, and starts at 100%. At 100% a slider changes nothing. Each acts on some of the five rows of colours (the rows of Colors in use) and on every colour Android takes from those rows, in light and in dark mode:

SliderRowsWhat it does to the phone
Accent saturationAccent 1, Accent 2, Accent 3Below 100% the accents get calmer, and at 0% they are greys. Above 100% they get stronger, as far as the screen can show. This covers the accent colours themselves, the tinted panels behind buttons and chips, the text on them, and the fixed accent colours, your own accents from Secondary and tertiary accents included. Backgrounds, surfaces, outlines and the text on backgrounds stay as they are.
Background saturationNeutral 1, Neutral 2Below 100% the backgrounds lose their faint tint of your colour, and at 0% they are pure greys. Above 100% the tint gets stronger. This covers the backgrounds, the surfaces (cards, sheets, panels), the outlines and the text on backgrounds, which carries the same faint tint. The accents stay as they are.
Background lightnessNeutral 1, Neutral 2The same colours as Background saturation: above 100% they get lighter, below 100% darker, in light and in dark mode alike. Only their lightness changes. The accents stay as they are.

No slider changes the colour Android uses for errors (its red, or CMF's own red): it is not part of these rows.

How far Background lightness goes. Android measures the lightness of its colours on a scale from 0 (black) to 100 (white). At 0% or 200% a colour moves ten steps on that scale, at 50% or 150% five, and so on. Colours close to white or black move less: the lightest shade of a neutral row after white (shade 10) moves a tenth as far as the middle ones, shade 50 half as far, and white (shade 0) and black (shade 1000) never move. So white stays white and black stays black. At 200% shades 10, 50 and 100 of the two neutral rows reach white; at 0% shade 900 reaches black.

The backgrounds merge at the ends. Android gives its backgrounds slightly different shades, so that cards, sheets and panels stand out from the background behind them. In light mode most of them sit at about 90 or higher on that scale, so at 200% they reach white: the background, the surface and the five panel colours (Android's background, surface, surface_bright and surface_container_lowest to surface_container_highest) become the same white, and in light mode panels no longer stand out from the background. With the 2025 colours the highest panel colour sometimes stops just short of white. At 0% the same happens to the darkest backgrounds in dark mode: background, surface, surface_dim and the two lowest panel colours become the same black (with the 2025 colours and CMF the middle panel colour too). Measured with six test colours, every style, on the maths for Android 14 and 16.

With Pure black backgrounds on, pure black wins where both name the same colour, as it does over a style from More styles: the dark backgrounds stay true black whatever Background lightness says.

What the two accents colour

Android's theme has three accent rows, the Accent 1, Accent 2 and Accent 3 of Colors in use, and from Android 14 it makes role colours from each: the accent itself, the text on it, a softer "container" colour for buttons and panels and the text on that, and four fixed colours that stay the same in light and dark mode. What the switch changes

A style makes three accent palettes from the source colour, one for each accent row (Accent 1, Accent 2 and Accent 3 of Colors in use), and two neutral ones. Every accent colour Android uses comes from one of the three accent palettes at some lightness, on Android's scale from 0 (black) to 100 (white): the shades of the rows at fixed steps (shade 100 at 90, a very light tint, and shade 300 at 70), and the role colours and fixed colours at the lightness the style and the Color spec give each of them.

  • On (the default): every colour keeps its own lightness. The colours are exactly those the app writes without the switch.
  • Off: in each of the three accent palettes, lightness 90 gives the colour of lightness 70. Every colour taken from them at exactly 90 is therefore darker: shade 100 of each accent row becomes the colour of its shade 300, and so does every role and fixed colour that sits at 90. The lightnesses themselves are not changed: a colour at 80 or at 95 keeps its colour, and where Android's contrast setting moves a colour away from 90, it keeps the colour of its new lightness.

Which role and fixed colours sit at 90 depends on the Color spec, the style and light or dark mode. With the other controls

The switch comes last. First the style makes its palettes from the source colour (your wallpaper's colour, the colour in the code field, or Google blue; see "Where the colour comes from" in More styles) at the chosen Color spec; then your Secondary and tertiary accents take the place of the second and third accent palettes; then the Intensity sliders adjust the palettes; and only then does lightness 90 of the three accent palettes take the colour of lightness 70. The shades are then made by the rule of the phone's version of Android, with shade 100 of each accent row in the colour of its shade 300, and the role and fixed colours are worked out at their usual lightness, at the phone's contrast. So with an accent of yours, the colours at 90 of your palette take your palette's colour at 70, and with Accent saturation moved, the colour they take is the adjusted one. The switch changes colours, not lightnesses: where Fidelity and Content choose the lightness of a panel by looking at the palette, they look at it as it is with the switch on. Pure black backgrounds names only neutral shades and dark backgrounds and surfaces, none of which the switch changes, so the two never name the same colour; with both on, the overlay carries both.

What can go wrong

Everything under "What can go wrong" in Root-only theme controls and in More styles holds here too: the repaint and the restarts (and the Undo bar after one), the colours falling back after a wallpaper change, a dark-mode switch or a restart of the system interface (tap Apply theme again; the app does nothing in the background to put the darker colours back), the refusal sheet with Android's reason, no answer, Super User gone in between, the theme setting refused first, Android answering with its own colour, not everything following the overlay, and the overlay staying listed as off; so do "The contrast setting" and "After an Android update" in Root-only theme controls. Because a style's colours are in the overlay, the messages, the sheet and the card's line use the theme overlay words: Theme overlay written, The theme overlay was not written, Could not write the theme overlay, and so on. What is different with the switch off:

  • Text on the tinted panels stands out less. The panels and the text on them were made to be far apart in lightness; the switch moves one of the two closer to the other. Computed on the app's colours for the example above (#6750A4, Tonal Spot, 2021), the contrast of the text on primary_container (on_primary_container) falls from 7.3:1 to 4.1:1 in dark mode on every supported version, and in light mode on Android 15's quarterly updates, on Android 16 and on Android 17; on Android 14 and on Android 15's first release, whose text on the panels is darker, from 13.3:1 to 7.5:1 in light mode. 4.1:1 is below the 4.5:1 that the usual accessibility guideline (WCAG) asks for small text. How it reads on a screen has not been looked at. The same goes for an app that puts dark text on shade 100 (reasoning, not measured: no app was looked at).
  • You may see little difference. At 2025 and 2026 few colours sit at exactly 90, and what an app shows depends on which colours it uses (see "Where you may see it" above). If nothing you use changes, turn the switch back on and tap Apply theme, so you do not keep an overlay you do not need.
  • The check does not look at these colours. After writing, the app asks Android for four of the colours it wrote (an accent shade 600, a neutral shade, primary in light mode and surface in dark mode; on Android 16 QPR1 and QPR2 the ones named in "Android 16's quarterly updates" in Root-only theme controls), none of which the switch changes (on Android 16 QPR1 and QPR2 measured with the six source colours, every style and spec). So the app does not see whether Android shows the darker colours; Colors in use shows the shades, once it redraws. Android 17 is the exception: one of the colours it asks for there, system_primary_fixed_dark (see "Android 17" in Root-only theme controls), sits at 90 with every style but Monochrome at 2021, and with most styles at 2025 and 2026 (and system_primary_dim_dark with Rainbow for one source colour), measured the same way; there the check does see the darker colour in that one.

None of this has been tried on a rooted phone yet. The colours were checked in tests against the app's colour maths from before the switch, with the rule applied by hand by a separate script, and against Google's colour library with its three accent palettes changed the same way, for every supported version of Android, every style and spec, with and without the Intensity sliders and the accents; Android 14's quarterly updates, which came to the app after the switch, only with the measurement above (six source colours, every style and spec, the standard and the middle contrast), which found the same colours at 90 as on the first release at the standard contrast. The write was checked in tests that imitate the phone. The first run on real hardware may find something these words do not say.

If it lists an app only after the app has asked for su, tap Request Super User first and allow this app when it asks. Otherwise open it yourself, allow this app, then tap Request Super User." About "temporary root"

The note on the card says that temporary root is granted inside your root manager. That is the whole of it: a grant is as temporary or as lasting as the manager makes it. Some managers let you allow an app once, for good or for a number of minutes; KernelSU, KernelSU Next and APatch only switch an app on or off in their list. A root set up by a manager can need to be set up again after a phone update. The app never keeps root for itself beyond the manager's answer. It asks su again when it needs to know (when the app starts with Root as the chosen mode, when you open Root Features while it reads ACTIVE, when you tap Request Super User, when you come back after Open root manager or Open manager, and when you tap Check Status on the Shizuku card of Working Modes), and that answer is what the chip shows until the next time it asks.

What you are getting into

  • From the moment the chip reads ACTIVE, everything this app does runs as root: it is no longer limited to what Android allows the shell user. That is the point, and the risk. Work the way Staying safe describes: one change at a time, back up first.
  • In a manager that offers a time limit, a lasting grant stays until you cancel it in the manager, across restarts of the app and of the phone. A grant for a number of minutes ends by itself when the time is up, and the manager asks again at the next root action. A "once" grant covers that one request only (see Way A). In the list managers, the switch holds until you change it.
  • The only things the app changes on its own here are its chosen working mode (Root, or the one you had after a refusal) and the test command id. It writes nothing to the system and changes nothing in the manager.
Undo. In your root manager, deny or remove ADB/Root Full System Toolbox from its list; then open Working Modes and choose another mode (Auto, Shizuku, Wireless Debugging or ADB over TCP). The chip reads AVAILABLE, or DENIED if the app has already seen the refusal (it asks su again when you come back through Open manager, or when you open this tab while it reads ACTIVE); Check Status on the Shizuku card of Working Modes clears that. The rows lock again either way. Your phone stays rooted: that is the manager's business, not this app's.

If it does not work

  • The chip reads NOT FOUND and stays there. The phone has no su that the app can see. With KernelSU, KernelSU Next or APatch, the likely reason is that this app is not allowed there yet: those managers show su only to the apps they allow. Tap Open root manager, allow the app in the manager's list and come back (Way B): the app then finds su and goes on from Way B step 4. Otherwise the phone is not rooted, or the manager is disabled, and nothing on this tab can change that.
  • The manager never asked. Use Way B and allow the app in the manager's list, then Request Super User again.
  • The app is not in the manager's list. Some root managers add an app to their list only once the app has asked for su. Tap Request Super User (Way A): the manager shows its question, and after that the app is in the list.
  • You allowed it in the manager, but the chip still reads DENIED. The app asked while the answer was still no, and keeps that answer until it asks again. Tap Request Super User; the new answer replaces the old one.
  • You allowed it, and the chip reads AVAILABLE. Root is not your chosen mode yet (you answered Cancel when the app offered to switch, or you opened the manager another way). Tap Request Super User, or choose Root in Working Modes.
  • "Root was denied or is not available" every time. See "If it does not work" in Root.

It opens your installed root manager, which exists only on a phone that is already rooted, so it is unlocked only with real root: the chip reading ACTIVE for Root with su granted, or a Shizuku server that is itself running as root (UID 0). Why it is behind the gate

What you are getting into

  • An app with root can do anything. It can read every other app's data, change the system, watch what you type and hide what it does. Switch one part of an app on or off, a screen (activity), a receiver, a service or a provider, without freezing the whole app. The switches live in the app menu's Activities and Components tabs; this row sends you there and explains why they need root.

Where it is: the Root Features tab, the second row of the Features card: "App components", "Enable or disable activities, services, receivers and providers for any app.", with the button Open apps. Locked (Locked, Needs Super User) until the chip reads ACTIVE.

Why this is a root feature

Android lets some users switch whole apps on and off (that is what Freeze does) but is stricter about a single part of an app. The ADB shell user (UID 2000) it refuses: Android's answer begins "Shell cannot change component state" unless the app is marked test-only in its manifest (android:testOnly). The root user (UID 0) and the Android system user (UID 1000) it allows. So the ENABLE and DISABLE buttons on a part unlock in Root mode (with su granted) and when your Shizuku server runs as the system user (UID 1000) or as root (UID 0). For the ADB shell user (UID 2000), which is Shizuku started over ADB, ADB over TCP and Wireless Debugging, and in Read-Only they carry a padlock, which here means "Needs Super User (Root)", and a tap sends nothing to Android. When they are unlocked the pm enable and pm disable commands run as the root user or the system user, and Android accepts them.

A tap on a locked ENABLE or DISABLE goes the Root way. On a phone with su the app switches the working mode to Root at once, as Request Super User does, and your root manager asks (KernelSU, KernelSU Next and APatch do not ask: they say no until you allow the app in their list, see Getting Super User). If it grants, the change goes ahead. If it says no, the mode you had comes back, the message reads "Super User was not granted. The working mode stays Shizuku ADB (UID 2000)." with the name of that mode, and the app asks "Enabling or disabling a component needs Super User. Open Root Features to check if your device supports Super User?". On a phone without su only that question comes. OK closes the app menu (or the Activity Launcher) and opens Root Features; Cancel leaves you where you were.

Step by step

  1. On Root Features, tap Open apps. The Application Manager opens and a message says "Open an app, then use its Activities and Components tabs to enable or disable each one."
  2. Find the app and open its menu (the ... button at the right end of its row, or press and hold the row).
  3. For a screen, open the Activities tab; for a receiver, a service or a provider, the Components tab. Each row has the part's name, tags (exported or unexported, disabled when it is off) and buttons: DISABLE or ENABLE, plus LAUNCH on a screen and STOP on a service. The app menu describes the two tabs in full.
  4. Tap DISABLE on the part. For a part of a system app the app asks first: "Disable Name of the system app package? This can break the app or the system UI. You can turn it back on here." (with the part's short name and the app's package name); Cancel changes nothing. A message says "Component disabled" and the row gets the disabled tag. If Android refused, the message says "Failed" and a results box titled Toggle component shows Android's own words.
  5. To put it back, tap ENABLE on the same row: "Component enabled".

What you are getting into

  • A disabled part is gone until you enable it. A disabled receiver no longer hears what it listened for (a start-up receiver means the app no longer starts with the phone, a notification receiver means no notifications), a disabled service no longer runs in the background, a disabled screen cannot be opened (the app may crash when it tries), and a disabled provider can crash other apps that read from it.
  • System apps are the dangerous ones. A part of the phone app, the keyboard, System UI, Settings or the launcher can be what makes calls ring or the screen unlock. Never disable a part whose job you cannot name. Debloating safely applies here with less to go on, because no community list rates single parts.
  • The change holds. It survives restarts of the app and of the phone, and updates of the app. Android's own Settings has no switch for a single part, Clear Data does not reset it (except for the rare app that asks Android to, a manifest flag on Android 13 and newer), and the Debloater's History and Undo do not cover it. The ways back are ENABLE on the same row, or pm enable with the full name of the part (package/class) in the Console.
  • It needs root every time. If Super User is taken back, a part you disabled stays disabled, and ENABLE is refused for the same reason DISABLE would be. Put parts back before you give root up.
Careful. Disable one part, then use the phone for a while, before the next. Keep a note of the full names of the parts you disable. If an app misbehaves, enable its parts again before you try anything else.

Switch off the parts of an app that belong to a known tracker (advertising, analytics, crash reporting), one app at a time or many at once, and switch them back on. It works where App components works: in the Root working mode with Super User granted, or with Shizuku running as the Android system user (UID 1000) or as root (UID 0).

Where it is: three places. The Trackers box of an app (the TRACKERS chip in its menu, see The app menu); Disable Trackers and Enable Trackers at the bottom of the batch sheet (see Selecting many apps); and the third row of the Features card on the Root Features tab, "Trackers in apps", "Switch off the tracker parts (ads, analytics) of any app.", whose Open apps button opens the Application Manager with the Trackers filter on and says "Open an app and tap its TRACKERS chip, or select apps and use Disable Trackers in the batch menu."

What a tracker part is

An app tells Android about its parts in its manifest: its screens (activities), services (work that runs in the background), receivers (they wake up when something happens, such as the phone starting) and providers (they hand data to other apps or start early). A tracker library often brings parts of its own; Google Firebase Analytics, for example, brings a receiver and services named com.google.android.gms.measurement.AppMeasurementReceiver and AppMeasurementService. The app compares the full name of every part with the same Exodus Privacy list the TRACKERS chip uses. A part counts only when a tracker's code name covers whole pieces of the part's name: com.tune (the Tune tracker) counts in com.tune.TuneTracker but not in com.tunein.player.Main, a part of the TuneIn Radio app itself. An app's own code never counts either: where a tracker's code name covers the app's own package, the tracker's maker is the app, and those parts are the app itself, not a library it carries. So the LiveMe app (com.cmcm.live) has no "Cheetah Ads" (com.cmcm.) parts, and Google Play services has no "Google Firebase Analytics" parts of its own measurement code, while another app that carries the same library shows them. Reading the parts needs no working mode; switching them does.

What switching off does. The app runs pm disable on each part (pm enable to switch it back on), then asks Android for the part's state and believes only that. A switched-off receiver no longer hears anything, a switched-off service no longer starts, a switched-off screen cannot be opened and a switched-off provider no longer starts early.

What it does not do. Most trackers also run inside the app's own code, which no switch reaches. A tracker with no part of its own says so in the box: "No part of its own to switch off: it runs inside the app's code." So switching off cuts what a tracker does through its own parts; it does not stop all tracking, and it is not a firewall. A shrinker (the tool that makes an app smaller) renames a library's inner code but not the names of the parts in the manifest, so those parts are still found; a tracker with no part of its own whose code was renamed is not seen at all.

The Trackers box

When the app has tracker parts, the box opens with a small card: "(number) tracker parts · (number) switched off", and two buttons, Disable all trackers and Enable all trackers. A button with nothing to do is greyed out (Enable all trackers until a part is switched off). Then, under each tracker's name and kind, a line such as "3 parts · 0 off" with that tracker's own button: DISABLE while any of its parts runs, ENABLE once none does. Under it, each part: the last piece of its name, its kind (screen, service, receiver or provider), and off when it is switched off, or off by default when the app itself ships it switched off. A tracker found only through its parts (its code was renamed, its part names were not) is listed too.

When it is locked. Without Super User or the system user the buttons carry a small lock, and the card says Needs Super User (Root). A tap goes the Root way, as the component switch does: on a phone with su the app switches the working mode to Root and your root manager asks (see Getting Super User); otherwise it asks "Switching trackers off or on needs Super User. Open Root Features to check if your device supports Super User?". Nothing is switched until it is unlocked.

Step by step: one app

  1. On Root Features, tap Open apps (or tap the Trackers pill in the Application Manager yourself). The list shows the apps a tracker was found in.
  2. Open the app's menu (the ... button at the right end of its row, or press and hold the row) and tap its TRACKERS chip. The Trackers box opens.
  3. Read the list. To switch off one tracker only, tap DISABLE under it. To switch off every one, tap Disable all trackers. For a system app the app asks first: "Switch off (number) tracker parts of the system app (package)? This can break the app or the system UI. You can switch them back on here." (for one part: "Switch off 1 tracker part ... You can switch it back on here."); Cancel changes nothing.
  4. A message says "Disabling tracker parts..." and the buttons grey out while it works. Then it says "Disabled (number) tracker parts", and the box shows what the phone now reports: the off tags, the counts and the buttons. The app menu's Activities and Components tabs show the same parts as disabled.
  5. If Android did not change some parts, the message says "Some tracker parts were not changed" and a Trackers results box lists each part with Android's answer.

Step by step: many apps

  1. Select the apps (the Trackers pill and Select All select every app a tracker was found in) and open the batch sheet with the round button.
  2. Tap Disable Trackers. A box "Confirm Disable Trackers" opens with the line "(number) apps selected • their tracker parts are switched off (Enable Trackers switches them back on)" (and, when system apps are selected, "system apps among them:" with their number, and that switching their parts off can break them or the system UI) and the list of apps. Tap Disable Trackers to go on, or Cancel.
  3. The progress bar runs as for any batch. Batch Results opens with the subtitle "DISABLE TRACKERS • (number) of (number) apps". Each app's card says what was switched off, tracker by tracker, how many parts were already off, and every part Android did not change. An app with no tracker part says "No tracker parts in this app: the trackers it holds, if any, run inside its own code." and counts as a success, because nothing failed.
  4. Enable Trackers works the same way but starts at once, without the confirmation box (as Enable does after Freeze).

How to undo it

  • Enable all trackers in the app's Trackers box, or ENABLE under one tracker.
  • Enable Trackers in the batch sheet, for many apps at once.
  • The History (the clock button in the UAD-NG Debloater): Disable all trackers writes a step "Disabled trackers in (app)", and the batch "Disabled trackers in (number) apps". The step keeps the names of the parts it switched off, and its Undo switches back on exactly those, app by app, also where Android refused some other part of the same app, and also a part that a newer tracker list (after Update the list) no longer counts as a tracker's: Undo Results lists it under "No longer on the tracker list", and says so when an update of the app removed a part. A step that switched nothing off has no Undo. Off the Super User gate, Undo of such a step goes the Root way first, as the switches do. The Undo writes a step of its own that keeps only the parts the Undo really switched back on (not one that was already on again), so undoing the Undo touches nothing else. A single tracker's DISABLE is not written there, as a single part's switch is not.
  • Each part's ENABLE in the app menu's Activities and Components tabs, or pm enable with the app's package and the part's full name in the Console.

Enable all trackers, ENABLE and Enable Trackers switch back on every tracker part that is switched off, whoever switched it off: this app, another debloater, or you in the Console. Undo is narrower, as above: only the parts its own step switched off. Neither touches a part the app itself ships switched off (off by default); it stays as the app wants it.

What you are getting into

  • Notifications can stop. Some trackers on the list also deliver push notifications: OneSignal, Pushwoosh, Urbanairship (Airship), Batch, Braze, LeanPlum and Pusher among them. Switch one of those off and the app may stop showing notifications. To keep them, use DISABLE under the other trackers instead of Disable all trackers.
  • An app can break. An app that opens a switched-off screen (an ad screen, a sign-in screen of a tracker's library) can crash or show nothing there. If an app misbehaves, switch its trackers back on before you try anything else.
  • The app is stopped while its parts change. Android applies a part's new state by stopping the app that holds it. Close anything you were writing in it first. For a system app such as System UI this can make the screen flash or restart.
  • System apps are the dangerous ones. Parts of Google Play Services, the phone app or System UI can be what makes other apps, calls or the lock screen work. Switch off the trackers of a system app only when you know what that app does, one app at a time.
  • The change holds. It survives restarts of the app and the phone, and app updates. Clear Data does not reset it; uninstalling the app and installing it again does.
  • It needs root every time. If Super User (or Shizuku as the system user) goes away, the switched-off parts stay off and switching them back on is refused for the same reason. Switch them back on before you give root up.
  • Not tried on a phone yet. This feature has been checked on a computer, not yet on a rooted phone or with Shizuku as the system user.
Careful. Start with one app you can do without, use it for a day, then go on. Leave the trackers of system apps alone unless you have a reason.

With Super User the File Manager works as root: it opens, copies, moves, renames, edits and deletes files anywhere, also in other apps' data and in the system folders, and a file's sheet gets Permissions… to change who may read, write and run it, and who owns it.

Where it is: Root Features, the row Root File Management; Open files opens the File Manager. In the File Manager, tap a file or folder (or its ⋮): Permissions… is the button before Delete. Both need the root user: Root as the working mode with su granted, or Shizuku running as root (UID 0). Shizuku as the system user (UID 1000) or over ADB keeps the row locked and shows no Permissions…. Added storage (a folder you picked through Android) has no permissions to change.

What Permissions… shows

  • A line Now: with the mode in digits and letters (for example 0644 (rw-r--r--)), the owner and the group with their numbers, and the SELinux label.
  • Permissions: ticks for Read, Write and Run for Owner, Group and Others, and the same as digits in a field (755, 0644). Either one changes the other. The special bits (setuid, setgid, sticky: the first of four digits) stay as they are unless you type four digits. Apply permissions changes the mode at once.
  • Owner and group: a user and a group, as a name (root, system, media_rw, u0_a123) or a number (0, 1000). Leave one empty to keep it. Apply owner asks first. A link is changed itself, not what it points to.
  • For a folder, Also everything inside this folder under each part changes the folder and every file and folder in it. It always asks first.
  • After a change the panel reads the item again, so what it shows is what Android now has, with a line Before the last change: that keeps the old values.

What you are getting into

  • Nothing stops you from breaking an app or Android. An app whose files you make unreadable to it, or that you hand to another owner, can crash or lose its data; system files with the wrong mode, owner or label can stop the phone from starting. Change only what you know.
  • The app refuses a few places outright: /, the top-level folders (/data, /system and the like), a storage root, the first levels of the system partitions, and this app's own data. It also never changes a whole folder of the system partitions at once.
  • The system partitions (/system, /vendor, /product) are read-only on almost every phone: a change there fails with Android's own message.
  • Permissions and owner do not change the SELinux label. A file copied or moved into another app's folder may keep a label that app cannot use; this app does not relabel files.

How to undo it

  • One file or folder: open Permissions… again, put back the values the Before the last change: line shows (it stays while the sheet is open on that item), and apply them. Note them down first if you will close the sheet.
  • Everything inside a folder: what each item inside had before is not kept, so there is no exact undo. For app data, Clear data of that app (the app's menu) gives it fresh files with the right owner; reinstalling it does the same. For your own storage, Android repairs the owner of shared storage by itself on the next restart in most cases.
  • A phone that no longer starts after a change to system files needs the same repair as any broken root change: your root manager's or recovery's way back, or flashing the firmware again. That is why the system folders are guarded.
