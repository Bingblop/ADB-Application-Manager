A working mode is the way this app borrows enough power from Android to freeze, remove and change other apps. You choose one once; the coloured badge at the top right of the screen always shows which one is in use.

Why the app needs a working mode at all

Android keeps every app in its own protected box. An ordinary app, this one included, cannot freeze, uninstall or change the settings of another app. Android reserves those jobs for two special users (a "user" here is an account inside Android, not a person): shell (user number 2000), which is the user that ADB runs as, and root. A working mode is simply a way for this app to send its commands as one of those two users.

  • ADB over TCP and Wireless Debugging let the app's own built-in copy of ADB talk to the phone's ADB service, from the inside, as the shell user.
  • Shizuku is a separate app that has already started a helper running as the shell user (or as root) and lets this app use it.
  • Root runs the commands as root through the phone's su program, which your root manager (Magisk, KernelSU or APatch) controls. The app counts Root as ready only when the root manager has really allowed it.
  • Read-Only is what you get when none of these is ready: the app can look, and cannot change.
  • Auto is not a route of its own. It tries some of the above in a fixed order, and uses the first that is ready.

The commands themselves are the ordinary Android ones (pm, am, appops, settings and so on). The app is just a convenient front end.

Which one should I pick?

Read down the list and stop at the first line that fits.

  1. Is your phone rooted? If yes, pick Root. It survives restarts and needs no Wi-Fi. (Auto never picks Root on its own, so you must choose it yourself.)
  2. Otherwise, is it Android 11 or newer? Settings, About phone, shows the version. If yes, pick Wireless Debugging. No computer is needed, only Wi-Fi.
    • If you tire of reconnecting every time the Wi-Fi changes, ADB over TCP can be switched on from Wireless Debugging with one button, and does not depend on the Wi-Fi once it is on, but it is switched off by every restart.
    • If you already use Shizuku and it is running, pick that instead; it is a single tap.
  3. Otherwise (Android 8 to 10, not rooted): you need a computer and a USB cable. Use it once to switch on ADB over TCP, or to start Shizuku. Both have to be redone after every restart. Without a computer, Read-Only is usually all this phone can do with the app.
  4. Not sure, or just browsing? Leave it on Auto or Read-Only. Nothing is lost.

How to change the mode

  1. Tap the badge at the top right of the screen. (The orange banner at the top of the Application Manager tab has a Set Up button that opens the same place.)
  2. A sheet called Working Modes & ADB Setup slides up. Under its title is a line such as "Selected: Automatic • Active: Setup Mode (Read-Only)", which tells you what you chose and what is actually in use.
  3. Find the card for the mode you want and use its button: Use Automatic, Connect then Use This Mode (ADB over TCP), the pair and connect steps (Wireless Debugging), Authorize & Use Shizuku, Request Root Access, or Continue in Read-Only. The button of the mode you are on changes to Selected (the Shizuku card shows the tag AUTHORIZED instead).
  4. A message at the bottom says what happened, the badge updates, and the list of apps is reloaded.

You may switch at any time, and nothing happens to your apps when you do. The app never changes the mode you chose by itself, except that Disconnect on a connected ADB mode drops you back to Auto. A tile in Android's quick settings can also cycle the mode without opening the app (Quick Settings tiles and widget).

Wireless Debugging is Android's built-in way to let an ADB tool connect over Wi-Fi. This app pairs with your own phone once, then connects, with no computer at all.

Before you start

  • Android 11 or newer. The feature does not exist on older versions; use ADB over TCP there.
  • A Wi-Fi connection. The phone must be joined to a Wi-Fi network (one without internet is usually fine). Wireless Debugging does not work over mobile data. If no Wi-Fi is around, joining the hotspot of another phone works on many phones.
  • Developer options switched on (step 1).
  • About five minutes. Pairing is needed once; connecting again later takes a minute.

Step 1: switch on Developer options

Android hides its developer settings until you ask for them.

  1. Open the phone's Settings and go to About phone. On a Samsung phone with One UI, go to About phone, then Software information.
  2. Find Build number and tap it seven times, quickly. Midway, a message counts down ("You are now 3 steps away from being a developer"). If the phone has a PIN, pattern or fingerprint, it asks for it.
  3. You see "You are now a developer!". A new entry, Developer options, now exists: on Samsung at the bottom of the main Settings list, on a Pixel under System.
Tip. Names differ by maker. On Xiaomi the item to tap is often called OS version or MIUI version; on OnePlus and Oppo it is under About device, then Version. If you get lost, type "Build number" in the Settings search box. The same trick finds "Developer options". The app also has an Open Developer Options button on the Wireless Debugging card.

Step 2: switch on Wireless debugging

  1. Connect to the Wi-Fi network you will use.
  2. Open Developer options and scroll to the Debugging section. Switch Wireless debugging on. Android asks "Allow wireless debugging on this network?". Tap Allow (tick "Always allow on this network" if you trust it).
  3. Tap the words "Wireless debugging", not just the switch. The Wireless debugging screen opens. It shows IP address & Port (something like 192.168.1.20:37099: the part before the colon is the phone's address on your Wi-Fi, and the number after it is the port, which picks one service on the phone to talk to), and the entries Pair device with pairing code (on some phones Pair new device with pairing code) and Paired devices.

This screen has two different addresses, and mixing them up is the commonest mistake. The table below keeps them apart.

AddressWhere Android shows itWhere it goes in the app

Connect address (IP address and Port)On the main Wireless debugging screen. Changes whenever Wireless debugging is switched off and on, or the phone restarts.Step 2 of the card: the IP and Port boxes.

Step 3: pair this app with your phone

Pairing is the one-time handshake in which Android learns to trust this app's key. The six-digit code only lives while Android's pairing window is on screen; if you switch to another app full screen, the window closes and the code stops working. The app gives you two ways around that.

Way A: split screen (the app's own tip)
  1. In this app, tap the badge to open Working Modes & ADB Setup and find the Wireless Debugging (Android 11+) card.
  2. Put Developer options and this app side by side, using Split Screen or a Pop-up Window from your phone's recent apps view, so both stay visible.
  3. In Developer options, tap Wireless debugging, then Pair device with pairing code. A window shows a six-digit code and an address with a port.
  4. In the app, under STEP 1: PAIR WITH CODE, type the address into Pairing address (for example 192.168.1.20:38475; typing only the port also works on many phones) and the six digits into Code. Tap Pair Device.
  5. A message shows adb's answer. Success reads "Successfully paired to ..." followed by an address.

The Auto-Detect Ports button looks for the pairing and connect addresses for you while the pairing window is open and fills in the boxes it finds. If it says "Nothing found", keep the Wireless debugging screen open and type them yourself.

Way B: pair from a notification
  1. In the app, tap Pair via Notification. On Android 13 and newer you must allow notifications first; the app says "Allow notifications, then tap Pair via notification again."
  2. A notification titled Pair over Wi-Fi appears, with a Pair button that opens a reply box. Go to Developer options, tap Wireless debugging, then Pair device with pairing code, and leave the six-digit window open.
  3. Pull down the notification shade. If the notification says "Found pairing service at ...", tap Pair and type just the six digits. Otherwise tap Pair and type the port, a space, and the code, like 37123 123456. When in doubt, type the port and the code.
  4. The notification changes to "Pairing...", then to "Paired with ... Open the app and connect." Failures are written there too, for example "That doesn't look like a 6-digit code".
Tip. You only need to pair once for each key. Android lists this app under Paired devices on the Wireless debugging screen, usually with a name that starts with adbmanager@ followed by your phone's model. Regenerating the app's key (Working modes) makes the old pairing useless, and you pair again.

Step 4: connect

  1. Back on the main Wireless debugging screen, read the IP address & Port.
  2. In the app, under STEP 2: CONNECT WIRELESS ADB, fill in the IP box and the Port box. Use My Wi-Fi IP fills in this phone's Wi-Fi address for you; Auto-Detect Ports can fill in the port. If you leave the IP empty, the app uses 127.0.0.1, which works on some phones; if it does not, use the Wi-Fi address.
  3. Tap Connect Wireless ADB. A message shows adb's answer, such as "connected to 192.168.1.20:37099".
  4. If the app finds the connection ready, it selects Wireless Debugging as your working mode.

What success looks like

  • The tag on the card changes to CONNECTED, and the button of the mode says Selected.
  • The badge turns green and reads "Wireless ADB (37099)", with your port in brackets.
  • The orange Read-Only banner on the Application Manager tab disappears, and buttons such as Freeze work instead of asking for a mode.

When the Wi-Fi changes or the phone restarts

Android picks a new random connect port every time Wireless debugging is switched off and on, and it often switches it off by itself when you leave the Wi-Fi network or restart the phone. The pairing stays; only the connect address changes.

  1. The badge turns orange. If you chose Wireless Debugging yourself, it reads "Wireless ADB (37099) (not ready)"; on Auto it reads "Setup Mode (Read-Only)".
  2. Switch Wireless debugging back on in Developer options and read the new IP address & Port.
  3. In the app, open the card, put the new numbers in the boxes (or tap Auto-Detect Ports) and tap Connect Wireless ADB. You do not pair again.

When the app starts and Wireless Debugging is your chosen mode, it tries the last address once by itself. That works only if the port has not changed.

Tip. Many phones let you add a Wireless debugging tile to the quick settings panel (Developer options, Quick settings developer tiles), which makes switching it on quick. If connecting is refused although the address and port are right, Android may have forgotten the pairing; pair again.

Common problems

  • Pairing says it failed. The code is wrong, or the pairing window closed and the code expired. Open the window again, and use split screen or Way B so it stays open. Check that the pairing address is the one in the pairing window, not the connect address.
  • "failed to connect", or a refused connection. The port is out of date, you used the pairing port, Wireless debugging is off, or the phone is on a different Wi-Fi from the one you allowed. Re-read the connect address and try again.
  • The message ends with "Target ... is not ready (check the authorization prompt on the device)". Android is waiting for an approval. Look for a prompt or notification and accept it, then tap Connect again.
  • Switch on Wireless debugging and it switches itself off. You are not on Wi-Fi, or the Wi-Fi was lost. Join a network first.
  • Auto-Detect Ports finds nothing. The pairing window must be open for the pairing address to be found, and some phones or networks block the discovery. Type the numbers yourself.
  • It worked, then stopped. Look at the badge. If it is orange, follow the steps in the section above. If it is green but actions fail, tap Connect Wireless ADB again.
  • Still stuck. See Troubleshooting. On a 32-bit phone, remember that the 32-bit build is new (Installing and updating the app).

ADB over TCP makes the phone's ADB service listen on a network port, 5555, so that the app's own copy of ADB can connect to it from the inside. It works on every Android version this app supports.

What it is

Normally ADB talks over a USB cable. The command adb tcpip 5555 tells the phone to listen on TCP port 5555 as well (a port is a numbered entry point for network connections). The app then connects to 127.0.0.1:5555, which is the phone talking to itself, so no computer is needed once the port is open. The app saves the address and tries it again when it starts, if Auto or ADB over TCP is your mode and the port is open.

Before you start

  • Developer options switched on, as in Wireless Debugging, step 1.
  • One of: a computer and a USB cable; or a Wireless Debugging connection on Android 11 or newer (see Way B below).
  • The setting does not survive a restart (see below), so keep this page handy.

Way A: the one-time step from a computer

  1. On the computer, get Google's SDK Platform-Tools, a small download that contains the adb program (download page), and unpack the folder.
  2. On the phone, in Developer options, switch USB debugging on (it lets a computer send ADB commands over the cable). Plug the phone into the computer with a USB cable. If the phone asks "Allow USB debugging?", tick "Always allow" and tap Allow.
  3. On the computer, open a terminal or command window in the platform-tools folder (on Windows, Command Prompt or PowerShell; on a Mac or Linux, Terminal) and run adb devices. Your phone should be listed with the word "device" beside it.
  4. Run adb tcpip 5555. It answers "restarting in TCP mode port: 5555".
  5. Unplug the cable. On the phone, open this app, tap the badge and find the ADB over TCP (Port 5555) card.
  6. Leave the address 127.0.0.1 and the port 5555 as they are, and tap Connect. A message such as "connected to 127.0.0.1:5555" appears. If Android asks "Allow USB debugging?", compare the fingerprint with the one on the This App's ADB Key card at the top of the sheet, tick "Always allow" and tap Allow.

Way B: without a computer (Android 11 and newer)

  1. Connect with Wireless Debugging first.
  2. On the ADB over TCP (Port 5555) card, tap Switch to 5555 (tcpip). The app runs adb tcpip 5555 through the Wireless Debugging connection, waits a moment and then connects by itself to the host and port in the boxes of the card (127.0.0.1 and 5555 unless you changed them).
  3. The Wireless Debugging connection may drop. That is expected, because the ADB service restarted.

If the message is an error such as "no devices/emulators found", there was no connection to switch from; connect with Wireless Debugging first. Some phones refuse the switch; the message then shows Android's reason.

Tip. A few custom Android versions (for example LineageOS) have a switch named ADB over network in Developer options that does the same thing as adb tcpip 5555. If yours has it, switch it on and use Connect.

What the card's buttons do

  • Connect connects to the host and port in the boxes. It also makes ADB over TCP your working mode if the connection is ready.
  • Use This Mode picks ADB over TCP as your working mode. If the app is not connected yet it tries to connect first; if that fails, the mode stays selected, and the badge says "(not ready)" when nothing is listening on the port.
  • Switch to 5555 (tcpip): described in Way B.
  • Disconnect drops the ADB connection. If ADB over TCP or Wireless Debugging was your mode, the app falls back to Auto.
Careful. Leave the host box at 127.0.0.1 unless you know why not. The host box accepts another device's address too, but the app's commands would then go to that device while its list shows this phone's apps. To work with another phone or a watch, use Connected Devices instead.

Why it is not persistent

The phone forgets the setting when it restarts. After every restart, ADB goes back to USB only, and the card shows DISCONNECTED. Repeat Way A or Way B. On Android 8 to 10 that means a computer again after every restart, which is the main reason Wireless Debugging, Shizuku or Root is nicer where you can have them.

How to tell it works

  • The tag on the card turns CONNECTED (green). PORT 5555 OPEN in orange means the phone is listening but this app is not connected yet, often because an approval is waiting; tap Connect.
  • The badge turns green and says "ADB TCP (5555)".
  • The orange banner on the Application Manager tab is gone and Freeze and friends work.

If it does not connect

  • "Connection refused" or "failed to connect". Nothing is listening on 5555: you have not done the one-time step yet, or the phone restarted since. Redo it.
  • "Target ... is not ready (check the authorization prompt on the device)". Approve the "Allow USB debugging?" prompt, then tap Connect again. If no prompt appears, in Developer options tap Revoke USB debugging authorizations, then try again.
  • The prompt shows a fingerprint that does not match the one in the app. Do not allow it; something other than this app is connecting. Tap Deny.
Careful. While port 5555 is open, the phone listens on the Wi-Fi too, not only on the inside. Another device on the same network could try to connect; it would still need your approval in the prompt, so never tick "Always allow" for a fingerprint you do not recognise. Use this mode only on a network you trust, and restart the phone when you are finished: that switches it off.

Shizuku is a separate free app that starts a helper with ADB-level power and lets other apps, this one included, use it. If you already run Shizuku, using it here is a single approval.

What Shizuku is

Shizuku is not part of this app and is not made by the same person. It is a small program you install and start. Once it is running, any app you approve can ask it to run commands as the shell user, "UID 2000": the user that ADB runs as, which is allowed to do things an ordinary app cannot. If Shizuku was started with root, commands run as root instead. This app shows "Shizuku ADB (UID 2000)" in its badge when it is using it.

The app also recognises an app called Shizuku Plus, which has its own package name.

Before you start

  • Android 8 or newer. Starting Shizuku on the phone itself, with no computer, needs Android 11 or newer.
  • Shizuku installed. Its official site, shizuku.rikka.app, explains where to get it (Google Play or GitHub). Install it like any other app.
  • Shizuku must be running before this app can use it. It stops whenever the phone restarts.

Starting Shizuku

Open the Shizuku app. Its main screen offers three ways to start; the wording differs a little between versions. Pick one.

Method 1: Wireless debugging (Android 11 and newer, no computer)
  1. Switch on Developer options and join a Wi-Fi network (Wireless Debugging, steps 1 and 2).
  2. In Shizuku, choose Start via Wireless debugging. Its own screen has a button to open Developer options and, on the first run, a Pairing step: Shizuku posts a notification where you type the pairing code from Android's pairing window. This is separate from the pairing this app uses.
  3. After pairing, tap Start. Shizuku shows a short log and then reports that it is running.
Method 2: from a computer
  1. Set up the computer and USB debugging as in ADB over TCP, Way A.
  2. Run the command that Shizuku shows on its screen. It is normally adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh.
Method 3: root
  1. In Shizuku, choose the option for rooted phones and approve the root request from your root manager.
  2. Shizuku has a setting to start by itself when the phone starts, for rooted phones.

Connecting this app to Shizuku

  1. Check that Shizuku says it is running.
  2. In this app, tap the badge and find the Shizuku ADB Service card. Its tag tells you where things stand.
  3. Tap Authorize & Use Shizuku. Shizuku shows its own question asking whether to allow ADB Application Manager Pro to use Shizuku. Tap the button that allows it (Shizuku's wording may differ a little between versions).
  4. A message says "Shizuku authorized. Using Shizuku mode.". The tag becomes AUTHORIZED, and the badge turns green and reads "Shizuku ADB (UID 2000)".

The card also has Open Shizuku, which opens the Shizuku app, and Check Status, which looks again. Authorizing Shizuku makes Shizuku your working mode, and it works alongside ADB over TCP.

Root means the phone has been modified so that apps can ask for full administrator rights. If your phone is already rooted, this mode is the simplest and the most lasting.

What root is

Android normally stops anyone from changing the system. Rooting adds a program called su (for "superuser") and a manager app that decides which apps may use it. The three managers this app names are Magisk, KernelSU and APatch. With root, a command runs as the all-powerful root user, one step above the shell user that ADB uses.

Risky. This app cannot root your phone, and it will not help you do it. Rooting is done with other tools, usually needs an unlocked bootloader (the program that starts Android, which is normally locked), normally erases the phone, usually voids the warranty and, on Samsung phones, permanently trips the Knox counter (a Samsung record that the phone was modified), which can disable Samsung Pay and Secure Folder. Do not root a phone just to use this app: Wireless Debugging or Shizuku does most of the same work on Android 11 and newer. If you root, back up everything first.

Before you start

  • The phone must already be rooted by you, with a root manager installed.
  • Know where the root manager's list of apps is, so you can see and cancel what you approve.

Step by step

  1. Tap the badge to open Working Modes & ADB Setup and find the Root (Superuser - su) card. The tag says AVAILABLE when the app can see a su program and Root is not your chosen mode, or NOT FOUND when it cannot see one. (ACTIVE and DENIED come later, once Root is your chosen mode: see below.) The app looks in the usual places, such as /system/bin/su, /sbin/su, /data/adb/ksu/bin/su and /data/adb/ap/bin/su, and asks the shell to find su.
  2. Tap Request Root Access. The app runs a test command through su (it asks for id) and waits up to fifteen seconds.
  3. Your root manager shows its own question. Tap Grant (or Allow). Choose "forever" only if you are happy to.
  4. If the answer comes back as root, the message says "Using Root (Superuser)". The tag becomes ACTIVE, and the badge turns violet and reads "Root (Superuser)".

If the answer does not come back as root, the message reads "Root was denied or is not available". Root stays your chosen mode anyway, but the app does not treat it as working: the tag turns orange and reads DENIED, the badge turns orange and reads "Root (Superuser) (not ready)", and no command that needs privileges runs. See "If it does not work" below.

How the app knows that root really works

Having a su program is not enough: your root manager may have refused this app. So, while Root is your chosen mode, the app asks su to run id and counts Root as working only when the answer says uid=0 (the root user). The four tags mean:

TagMeaning
NOT FOUNDNo su program on the phone.
AVAILABLEA su program exists, but Root is not your chosen mode. The app has not asked it anything, so no root prompt appears.
ACTIVERoot is your chosen mode and su answered uid=0. The badge is violet.
DENIED (orange)Root is your chosen mode, but su did not answer uid=0: your root manager refused this app, or you did not answer in time. The badge reads "Root (Superuser) (not ready)".

The question is asked only while Root is your chosen mode, and the answer is kept. It is asked again only when you check on purpose: Request Root Access, or Check Status on the Shizuku card. The app waits about eight seconds for you to tap Allow in your root manager's prompt (up to fifteen after you tap Request Root Access), so be ready to tap it. If Root is already your chosen mode when the app starts, the root manager may show that question the first time the app checks.

Tip. Auto never chooses Root. Its list is ADB over TCP, Wireless Debugging, then Shizuku. On a rooted phone, choose Root yourself with this button, once; the choice is remembered.

What root unlocks in this app

  • Every action runs as root. Freeze, uninstall, permissions, app ops and the rest all go through su, so they are not limited to what the shell user may do. The APK Installer/Updater, the working-mode shell in the Terminal and the Debloater all work in this mode, and the Installer lets you choose Root as the authorizer.
  • Backups of app data. Backing up an app's APK, permissions and app ops works in any working mode, but including its data (logins, saved games, settings) is root-only. The Backup sheet says "Uses Root. The app is stopped while its data is copied." Without root, the switch is greyed out with the words "Needs Root, which was not found on this phone." Restoring data needs root too (Backups).
  • Removing system apps directly. With ADB or Shizuku, if Android refuses to remove a system app for your user, the app tries a fallback (a direct call to Android's package service); with root the app does not use that fallback. In every case the app's file stays in the system area.
  • Root reaches places the shell user cannot, such as other apps' private folders. That is how data backup works.

Risks

  • Anything a root command can do, an app with root can do. Only grant root to apps you trust, and review the root manager's list now and then.
  • Root makes it easier to damage the system by mistake, for instance with the Unsafe items of the Debloater or by editing hidden settings. Read Debloater safety and Safety.
  • Some banking and payment apps refuse to run on a rooted phone.

If it does not work

  • Tag says NOT FOUND. No su was found. The root manager may not be installed or may have been disabled. Fix that, then open the sheet again or tap Check Status on the Shizuku card, which re-checks everything.
  • "Root was denied or is not available". You tapped Deny, or the root manager did not answer in time. Tap Request Root Access again and approve it, or look for the app in the root manager's list and allow it there.
  • Tag says DENIED, and the badge says "Root (Superuser) (not ready)". su exists but did not answer as root for this app, so nothing privileged runs. Open your root manager (Magisk, KernelSU or APatch), find ADB Application Manager Pro in its list of apps, set it to allow, then choose Root again with Request Root Access in Working Modes. If you allowed it after the question had timed out, the tag stays DENIED until you do this.

Auto picks the first working mode that is ready. Read-Only is what remains when none is: you can browse and inspect, but not change anything.

Auto mode

Auto is the default and is called Automatic (Recommended) on its card. It does not create a connection of its own; it looks at what is ready and uses the first of these, in this order:

  1. ADB over TCP, if the app is connected to 127.0.0.1:5555.
  2. Wireless Debugging, if the app is connected to the address you last used.
  3. Shizuku, if it is running and this app has been approved.
  4. ADB over TCP again, if port 5555 is open but the app has not connected yet: it connects quietly and uses it.
  5. Otherwise Read-Only.

Root is never part of this list. The Automatic card lists only "ADB TCP, Wireless Debugging, Shizuku". When the app starts with Auto (or ADB over TCP) on and port 5555 open, it connects to it by itself.

When Auto has found something, the badge reads "Auto" followed by a dot and the mode, for example "Auto • Wireless ADB (37099)". Auto changes its mind when things change: if the Wi-Fi drops, it falls back to the next ready mode, or to Read-Only. Pinning a specific mode instead stops that, and the badge goes orange with "(not ready)" if that mode is not available.

Read-Only mode

Read-Only is the safe mode. It is what the app starts in on a phone with nothing set up, and you can also choose it on purpose with Continue in Read-Only. The badge then says "Read-Only Mode" (chosen) or "Setup Mode (Read-Only)" (nothing ready), in orange.

What you can do
  • See every app, with search, sort, filters and the count boxes.
  • Open an app's menu and read its permissions, app ops, components and its decoded manifest, and use App Info to open Android's own page for the app.
  • Export the list or share it as a CSV file, copy package names, make saved lists.
  • Extract APK: copy an installed app's file out of the phone.
  • Browse files that the app is allowed to read (see permissions), including added storage such as an SD card.
  • Download the Debloater list and read its advice, check for updates, change themes and the app's own settings, and read the Device Specs in About.
What you cannot do
  • Freeze, enable, suspend, force stop, clear data, uninstall, reinstall, or launch an app through the menu.
  • Run batch actions, apply profiles, or make or restore backups.
  • Switch permissions, app ops or components on and off.
  • Read the log in the Logcat Viewer, change Hidden Settings or overlays, or use the working-mode shell in the Terminal. The Task Manager works only in part: its CPU, RAM, battery and network views work, but its process list and GPU view need a working mode.
  • Trim the caches of every app (Trim Caches in the SD Maid tab, see SD Maid). The button shows a padlock.
  • Install silently. The No privilege choice of the APK Installer's Authorizer setting hands the file to Android's own installer, which asks you to confirm. This app is listed under Android's "Install unknown apps" (it has its own row, Install unknown apps, in the Permissions sheet), and Android asks whether to allow it the first time an install is made this way.

The orange banner

At the top of the Application Manager tab, in Read-Only, an orange banner says "Active Mode: Read-Only (Unprivileged)" and "All installed apps are shown. To enable Freeze, Uninstall, or ADB commands, connect via ADB TCP 5555, Wireless Debugging, Shizuku, or Root."

  • Set Up opens the Working Modes sheet.
  • The X in its top right corner puts the banner away until the app is started again or Read-Only mode returns. It comes back the next time the app starts, and also if a working mode comes on and later goes away, so Read-Only does not hide itself for good.

The lock symbol

In Read-Only, buttons that would change something show a small lock and look dimmed: the permission buttons (GRANTED, REVOKED, DENIED), the app-op mode buttons (the lock is on the mode that is set), and the ENABLE, DISABLE and STOP buttons of an app's components, and LAUNCH (SHELL) for components that are not exported. A tap still helps: instead of doing nothing it opens a sheet called Working Mode Required, which says which action needs one and offers Set Up Working Mode or Cancel. With a working mode on, the locks go away, except on install-time permissions, which nobody can change (Words you will see).

Tip. Starting in Read-Only costs nothing and risks nothing. You can look around, learn what your phone has, and set a working mode up when you are ready. See Working modes to choose.

Every Android permission and special access the app asks for, what it is for, what stops working without it, and whether you can say no. Nearly all of them are optional.

Three kinds of permission

  • Ordinary permissions are granted automatically when you install. You never see a question, and Android does not let you switch them off.
  • Permissions with a pop-up are asked about by Android when needed ("Allow notifications?"). You may say no.
  • Special accesses have no pop-up. Android keeps each on a screen in its Settings. The app offers them in a sheet.

The permissions sheet

The first time the app opens, a couple of seconds after the list appears, a sheet called Allow a few permissions slides up. At the top of this first-launch sheet is a Language drop-down: the app starts in the language of your phone when it has it (Español, Français, Deutsch and the others listed under Language) and in English otherwise, and the drop-down changes it at once. You can open the sheet again at any time from the About tab, with the Permissions button; there it is called Permissions, and it says "Allow what you like and skip the rest: every one can be changed later."

  1. Each row has a name, a one-line reason, and either an Allow button or a tick and the word "Allowed".
  2. Tap Allow on a row to open the Android screen for it (switch it on, then press Back to return), or, for the ones the app can grant itself, to grant it at once.
  3. Allow all: with a working mode on, the app grants at once everything that has a command (Allow Restricted Settings first, then the rest) and starts again so that it all takes effect. What has no command, or what the phone refused, is opened one Android screen after another; closing the sheet cancels the rest.
  4. Not now closes the sheet. When everything is allowed, the same button says Done. If you allowed something while the first-launch sheet was open, closing it starts the app again so that the change takes effect everywhere.

On Android 10 and older there is no "All files" switch, so Allow shows Android's ordinary storage question instead.

Separately, when you do something that needs file access and the app has neither that nor a working mode, it opens the same sheet with only that one row, headed "File access needed", and carries on once you allow it.

Install unknown apps

The app declares the permission that Android calls Install unknown apps (its code name is REQUEST_INSTALL_PACKAGES), and the Permissions sheet has a row for it (see the table above). It is used only when the app hands an APK file to Android's own installer, which happens when an install is made without a working mode (for example the APK Installer's No privilege choice, or the app's own update without a working mode). Android lists this app under Install unknown apps, in its Settings, and asks whether to allow it the first time. If you say no, those installs are refused; installs through a working mode are not affected. Allowing it from the sheet beforehand avoids that question.

What it does not ask for

The app has no permission for the camera, the microphone, your location, contacts, calendar, messages, call log or accounts. It is not an accessibility service or a device administrator.

Tip. Do not mix up the two uses of "Install unknown apps". When you download this app, the switch that matters is the one for the app you download with, such as your browser (Installing and updating the app). The switch for this app itself (the row Install unknown apps in the Permissions sheet) only matters when it hands a file to Android's installer. Setting up a working mode avoids that step, because the app then installs the file itself.

To take anything back, open Android's Settings, then Apps, then ADB Application Manager Pro, and look under Permissions. Special accesses are under Settings, Apps, Special app access (the names vary by phone), or just use the sheet in About again. See also Privacy.
