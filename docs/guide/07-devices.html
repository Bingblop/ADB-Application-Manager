Look after another Android device from this phone: a Wear OS watch first, but a tablet or a second phone works the same way. You can manage its apps, send apps to it, run commands on it, read its log, browse its files and change its settings and screen density, all through ADB (the tool that talks to an Android device, see the glossary).

Where to find it: the tab bar, after Task Manager and before About. If it is not there, it has been switched off in the Feature List.

Before you start

  • On this phone: you do not need to set up a working mode when you reach the other device over Wi-Fi. The app carries its own copy of adb and uses it for this tab, so nothing from Working modes has to be on. The one exception is the Bluetooth link to a Wear OS watch, which needs ADB in a Working mode (see Adding a device).
  • On the other device: Developer options turned on (a hidden menu in its Settings, opened by tapping Build number seven times: Wear OS, start to finish shows how), and debugging turned on inside it. On a phone or tablet that is Wireless debugging. On a Wear OS watch it is ADB debugging and then Debug over Wi-Fi.
  • For the Wi-Fi way: both devices on the same Wi-Fi network.
  • A few minutes and the other device in your hand. The first connection needs you to read a number off its screen and to tap Allow on it.
Tip. If you have never done this, open Wear OS, start to finish first. It walks through a watch from a blank start to an installed app, one screen at a time.
Careful. Whatever you do in this tab happens on the device you picked at the top, not on this phone. The other tabs of the app act on this phone; this one never does. Before you disable, uninstall, delete or change something, read the device name in the card at the top so you are sure which device you are looking at.

Good to know

  • When you switch to another device in the picker, everything read from the first one (its app list, its log, its files) is thrown away and read again for the new one.
  • Pressing Back closes an open sheet first. After that it takes you to the tab you came from, as everywhere in the app. Leaving this tab does not stop a send or a command that is already running, but it does stop the 6-second device check and the live log. Only when Back is about to close the app does it ask first, if apps are being sent, a command is running or a batch change is being applied: it says "Press back again to leave" and then "Leave now?", because closing the app would cut the work short.
  • The live log (Play in the Logcat sub-tab) stops by itself when you leave the Logcat sub-tab or this tab.
  • Everything runs over adb between this phone and the device. Nothing goes through the internet.

Before this phone can manage a device it has to be introduced to it. The Add device sheet has three ways: type the address yourself (Wi-Fi), let the app look for devices on your network (Nearby), or link a Wear OS watch through its Bluetooth connection to the phone (Bluetooth).

Where to find it: in Connected Devices, tap + Add device (next to the device picker, or in the middle of the screen when no device is connected). The Send sub-tab also has a Bluetooth link button that opens the sheet on the Bluetooth tab.

Before you start

  • The other device has Developer options on (how to turn them on is in Wear OS, start to finish; on a phone or tablet, tap Build number seven times in its About screen).
  • For Wi-Fi and Nearby: debugging over Wi-Fi is on in the device, and both devices are on the same Wi-Fi network. This phone needs no working mode.
  • For Bluetooth: ADB must be on in this phone's own Working mode (ADB TCP or Wireless Debugging; tap the mode badge at the top right of the app to open the Working Modes sheet), and the watch must be connected to this phone through the Wear OS app.

Wi-Fi: two steps, pair and then connect

Wireless debugging uses two different addresses on the other device. Pairing is a one-time handshake that uses a 6-digit code. Connecting is what you do every time. They use different ports (the number after the colon), so do not copy one into the other's box.

DeviceWhere the pairing code and its address areWhere the connect address is
Phone or tablet (Android 11 or newer)Developer options, Wireless debugging on, then the button for pairing with a pairing code. A box shows a 6-digit code and an address with a port.The main Wireless debugging screen, line IP address & Port.
Wear OS watchDeveloper options, ADB debugging on, Debug over Wi-Fi on, then Pair new device (the pairing screen with a code). Menu names differ a little between makers.The Debug over Wi-Fi line shows the watch's address and port.
Step 1 of 2: Pair (first time only)
  1. On the other device, open the pairing screen. It shows a code and an address like 192.168.1.20:37215. Keep that screen open: the code only works while it is shown.
  2. In the sheet, on the Wi-Fi tab, type the address and port into the first box (the label starts with "1. Pair") and the 6 digits into Pairing code.
  3. Tap Pair. The grey box says Pairing..., then shows adb's answer. On success it says Successfully paired and a message at the bottom says Paired. Now connect. If the second box was empty, it gets the device's address filled in up to the colon, with the cursor ready for the port.
Step 2 of 2: Connect
  1. Close the pairing screen on the device. Look at its main wireless screen and read the address and port (not the pairing port).
  2. Type it into the second box, the one labelled "2. Connect" (for example 192.168.1.20:5555).
  3. Tap Connect. After a moment the sheet closes, the device appears in the picker, a message says Connected to and its address, and the device card shows.
  4. The device may ask Allow debugging? on its own screen. Tap Allow and tick Always allow. Until you do, the card says Not allowed yet.
Tip. Some older watches show only Debug over Wi-Fi with an address and no pairing screen. If yours does, skip step 1 and go straight to Connect. On a phone or tablet the connect port usually changes each time you switch Wireless debugging off and on, so read it again each time.

If the address or code is typed wrongly the app tells you before it runs anything: Type the address and port, like 192.168.1.20:37215, The pairing code has 6 digits, or Type the address and port, like 192.168.1.20:5555. The last one only appears when the connect address is empty or has odd characters; if the port is missing, adb decides what to do with the address.

Nearby: let the app look

Devices that offer wireless debugging announce themselves on the Wi-Fi network (the method is called mDNS). The Nearby tab asks adb who is announcing.

  1. Turn on Wireless debugging (or Debug over Wi-Fi) on the other device. If it is not paired yet, open its pairing screen and leave it open.
  2. In the sheet, tap Nearby, then Scan the network. It says Looking... for up to 15 seconds.
  3. Each device found is a row with its address in large letters and a grey line with its name and one of two states: waiting for a pairing code (button Pair) or ready to connect (button Connect).
  4. Tap Pair: the sheet jumps to the Wi-Fi tab with the pairing address already typed, and the cursor is in Pairing code. Type the code and continue as above. Tap Connect: the app connects at once.

If nothing is found you read Nothing found. Both devices must be on the same Wi-Fi network, with wireless debugging on. You can also type the address by hand under Wi-Fi. Some routers hide devices from each other (guest networks, "client isolation"), and not every device announces itself, so a failed scan does not mean the device cannot be reached: type the address by hand.

Bluetooth: a Wear OS watch with no Wi-Fi

A Wear OS watch is linked to its phone by Bluetooth through the Wear OS app. The Wear OS app can pass adb messages along that link. This app does it in two moves. First it opens a numbered entry point (a "port") on this phone that leads to the Wear OS app's adb hub. Then it connects to that entry point as if it were a device at 127.0.0.1 (the address that always means "this phone itself").

  1. On the watch: Settings, Developer options, ADB debugging on, then Debug over Bluetooth on.
  2. In the Wear OS app on this phone: Watch settings, Advanced, Debugging over Bluetooth on.
  3. Turn on ADB in this app's Working mode, so this phone can reach itself (ADB TCP or Wireless Debugging).
  4. In the sheet, tap the Bluetooth tab. Leave Local port at 4444 (a free number on this phone: any number from 1024 to 65535 is accepted, except one that this phone's own ADB uses) and tap Connect over Bluetooth.
  5. The grey box says Looking for this phone's own ADB..., then Linking to the watch through Bluetooth.... When it works the sheet closes and a message says Connected over Bluetooth. Allow it on the watch if it asks. The card shows the badge Bluetooth link.
  6. Look at the watch and tap Allow if it asks.

If this phone has no working ADB mode, the grey box says This phone is not connected to its own ADB. Turn on ADB in this app's Working mode first (Working Mode button at the top), then try again. The "button at the top" is the mode badge at the top right of the app. If you typed a port that this phone's own ADB uses, a message says That port is used by this phone's own ADB. Use another, like 4444. If the link fails, adb's words are shown, followed by a reminder to check that Debugging over Bluetooth is on in the Wear OS app and on the watch.

Careful. The Bluetooth link relies on the Wear OS companion app and on the watch's Debug over Bluetooth setting. It was written to follow the method Google documents for Wear OS, but it has not been tried on every watch. A watch that uses a different companion app, or that has no Debug over Bluetooth option, will not work this way. Use Wi-Fi then. Also keep the port at 4444 or another free number: the app refuses a port that this phone's own ADB uses (5555 by default), because that address stands for this phone itself and is kept out of the device list.

Recent addresses

Each time Connect works, the address is remembered (the last 8). When you open the sheet with an empty Connect box, the newest one is typed in for you. With no device connected, the same addresses are on the empty screen after Recent:; tap one to connect straight away. A Bluetooth link is not listed there: connect it again from the Bluetooth tab.

Disconnect

Open the device's three-dot menu and tap Disconnect. The device vanishes from the picker, and the empty screen returns if it was the only one. The device is still paired, so you can connect again with Connect or from Recent:.

The Apps sub-tab lists every app on the other device and lets you switch one off, remove it, bring a removed system app back, stop it, clear its data or copy its APK to this phone. It is the same idea as the Application Manager, but for the other device.

Where to find it: Connected Devices, sub-tab Apps (the first one). It reads the list by itself the first time you open it.

Before you start

  • The device must show Connected (see Connected Devices).
  • Reading the list can take a while on a slow watch: up to 90 seconds are allowed. The line above the list says Reading the apps of the device... until it is done.
  • Nothing here needs root on the device. The device's own rules still apply, so it will refuse some changes (see "When the device refuses" below).
Careful. Removing the wrong system app from a watch can break its clock face, its notifications or its pairing with the phone. Read Debloater safety before you remove anything you do not recognise, and Disable an app before you decide to uninstall it.

The list

Each app is a row with:

  • An icon: the real icon when this phone has the same app, otherwise a square with the app's first letter.
  • The name. When this phone has the same app installed, the name is the one this phone shows. Otherwise the app makes a name from the package name (the app's unique code name): it takes the last part, adds the part before it for very generic words such as app or wear, splits joined words and gives it a capital letter. So com.google.android.deskclock becomes Deskclock.
  • The package name in small letters under it.
  • Badges: UNINSTALLED or DISABLED when that applies, and always SYSTEM or USER.
  • A round-edged button on the right (Disable, Enable or Reinstall) and three dots for the menu.
  • A tick box on the left. Tap the box, or the name, to select the row.

The list is sorted by name. Under the search box a line tells you how many apps are shown (12 apps of 87). Only the first 600 rows are drawn; if there are more, a note says how many are hidden and suggests you search or filter. Reload, next to the search box, reads the device again.

What the commands really are

The names on the buttons stand for these commands, which the app sends to the device. You can run any of them yourself in the console.

ButtonCommand on the deviceEffect
Disablepm disable-user --user 0 PACKAGESwitches the app off for the main user. Reversible.

Pull APK: copy an app to this phone

  1. Tap the three dots of an installed app, then Pull APK.
  2. A message says Pulling 1 file... (or more, when the app has split files, see Split APKs).
  3. When it finishes you read Saved to Download/ADB App Manager/Devices/ followed by the device's folder.

The files go to the Download/ADB App Manager/Devices/<device>/ folder of this phone, where <device> is the device's address with the colon changed to an underscore (for example 192.168.1.20_5555). If the message says the folder could not be made, the app has no permission to write there: see App permissions.

When the device refuses

Some apps are protected. The device may answer with words such as Failure, Permission Denial, Operation not allowed or Shell cannot change component state. The sheet That did not work shows that answer. This is the device saying no, not a fault of the app. What you can do:

  • Leave that app alone. It is protected on purpose, often because the device needs it to run.
  • Try Force stop instead, which is allowed for most apps.
  • For a batch, the others still went through. Select just the failed ones if you want to try again.
  • If an app you disabled makes the device behave oddly, tap Enable on it. Use the Disabled filter to find it.
Risky. Uninstalling or disabling a system app can leave a watch stuck on a boot screen or without its watch face. Before you remove anything, make sure you can undo it: Disable can be undone with Enable, and an uninstalled system app can come back with Reinstall. If a watch no longer starts properly, a factory reset (done on the device) is the last resort and wipes it.

The Send sub-tab installs apps on the other device. You can choose package files stored on this phone, or send an app that this phone already has. It goes over the same connection the device uses now: Wi-Fi, USB or the Bluetooth link.

Where to find it: Connected Devices, sub-tab Send (the second one).

Before you start

  • The device must show Connected. Otherwise tapping Send to device says Choose a connected device first.
  • Have the files ready on this phone. The app accepts APK, APKS, APKM and XAPK files (and a ZIP that holds APKs). If you do not know the difference, read Split APKs and bundles.
  • For a watch, use an app made for Wear OS. A phone app may install but not be usable on a round, small screen.
Careful. Install only files you trust. An app sent to a watch runs with the same powers as one installed any other way. The device may also refuse an app that is meant for a newer Android than it has.

Step by step

  1. Open the Send sub-tab. The card Send apps to this device says Nothing chosen yet.
  2. Tap Choose package files. Android's file chooser opens. Pick one or more files and confirm. The files are copied into the app first, so a big file takes a moment.
  3. Or tap From this phone to send an app that this phone already has (see below).
  4. The chosen items appear as rows, each with a name and a grey line, and a cross to remove it. Clear list removes them all.
  5. Set the four switches, if you need to (below).
  6. Tap Send to device. A bar and a line show how far it is: for example 1 of 3 · face.apk · Installing 2 files.
  7. When it ends each row says Installed in green, or shows the end of the device's error in red. A line says 2 of 3 packages installed and a message says Sent to the device or Some packages did not install.

How bundles are trimmed to the device

An APKS, APKM, XAPK or ZIP bundle can hold a base app and dozens of "config" parts: one for each processor type, each screen density and each language. A watch needs only a few. When you send a bundle, the app asks the device what it has and keeps:

  • the base app and any feature parts, always;
  • of the processor parts, the first one that matches the device's processor list (best first); if none matches, all of them stay, because it is better big than broken;
  • of the density parts, the nearest one to the device's current density (the larger one on a tie); if the density is unknown, all stay;
  • of the language parts, the device's own language and English.

The device's language, density and processors are read when you pick the device. If you changed the density on the Display sub-tab, the new value is the one used. The row for such a bundle says Reading the package file while it is being opened, then Installing 3 files (the count after trimming).

Game data (OBB) in an XAPK

An XAPK can carry extra files for a game or app, stored under Android/obb/ or Android/data/. After the app has installed successfully, the app copies these files into the device's /sdcard/Android/... folders, one by one, and the line says Copying and the file's name. If copying fails, the row is marked as failed even though the app itself is installed.

Two kinds of line: for the device, and for adb

A line is sent in one of two ways.

  • Mode $ (the default). The line is run in the device's own shell, as if you were typing on the device. Pipes (the vertical bar), quotes and searches work the way the device understands them, for example ps -A | head -25.
  • A line that starts with adb . In $ mode, if the line begins with the word adb and a space, the rest goes to adb itself, not into the device's shell. This is how you copy files: adb pull, adb push, adb forward.
  • Mode adb. Tap the $ button and it turns into adb. Now every line goes to adb itself, and the hint in the box becomes pull /sdcard/Download/a.txt /sdcard/. You do not need to type the word adb in this mode; if you do, the app drops it. A command for the device's own shell then needs the word shell in front, for example shell ls /sdcard. Tap the button again to go back to $.

For adb lines the app adds the chosen device for you (adb -s THE-DEVICE ...). A few commands do not belong to one device and run without it: devices, connect, disconnect, pair, mdns, version, help, reconnect and keys. So does a line that starts with -s and a device name: you chose the device yourself. Quotes in an adb line are understood, so a name with spaces can be wrapped in quotes.

Which adb commands are blocked, and why

This app uses a single adb server (the background program that carries every adb connection) for everything it does: this tab, the Working modes, installs and the rest. If you stopped or restarted that server, every connection would drop at once, including the app's own working mode. So an adb line (one that starts with adb, or any line in adb mode) is not sent when:

  • it has kill-server, start-server, server or nodaemon anywhere before the word shell (they stop, start or change the server; what comes after shell is for the device and is not checked);
  • its first word starts with -P, -L or -H (they point adb at a different server).

Instead of running it, the console prints That one would stop the adb this app runs on, so it is not sent. in red. Nothing happened on the device. If you really need to restart the connection to one device, use Reconnect (shown under the card when a device is offline) or Disconnect in the device menu, then connect again.

What the output looks like

Plain text, exactly as the device prints it. A command that prints nothing, such as one that worked silently, shows nothing under it. Time limits and commands that never end

  • A device command may run for up to 2 minutes. An adb line (a pull or a push of a big file) may run for up to 10 minutes. After that adb is stopped and the answer ends with [Process timed out after ...ms].
  • Some commands never finish by themselves: logcat without -d, top without -n 1, adb logcat, ping without a count. Tap Stop to end them. Use the chips' forms, which end by themselves.
  • The console has no keyboard link to the device, so programs that wait for you to type (an editor, a login, su) cannot be used.
  • While a command runs, pressing Back until the app is about to close asks first, because closing the app would cut the command short.

If it does not work

  • Nothing happens on Run: a line that is empty is ignored.
  • "Permission denied" or "not found": the shell user may not be allowed that command, or the device lacks it. Not every command exists on a watch.
  • Red error that starts with adb's own words: read it. A typo in an adb word gives an answer such as adb: unknown command.
  • adb says "unknown command" for something that works in the device's shell (such as ls): you are in adb mode, where every line goes to adb itself. Put shell in front, or tap the button to go back to $.

How the rows are drawn

Exactly like in the Logcat Viewer tab. Each entry is one row:

  • A small coloured badge at the left with the level letter: V, D, I, W, E or F. The row has a coloured stripe on its left in the same colour.
  • The tag in bold: the part of the system or the app that wrote the line.
  • The time, and two numbers such as 1234/1256: the process and the thread that wrote it.
  • The message below, in the colour of its level. Several lines that belong to one log call, such as the lines of a crash report, are joined into one row.

Reading a crash on a watch

  1. Set the level to Error and the number of lines to 1000.
  2. Tap Clear, so only fresh lines show.
  3. Make the app crash on the watch (open it again).
  4. Tap Refresh. You see a few red rows.
  5. Look for a row with the tag AndroidRuntime whose message starts with FATAL EXCEPTION. The lines joined under it are the crash report: a line with Process: and the package name, then the name of the problem (for example java.lang.NullPointerException) and a list of lines that start with at. A line starting with Caused by is usually the real reason.
  6. Type the app's package name in the filter box to cut the noise. A crash in native code looks different: search for Fatal signal.
  7. Tap Copy or Share to send the text to the app's developer.

If it does not work

  • The area shows adb's complaint instead of rows: the device dropped or went offline. The live reading stops by itself. Fix the connection (see Connected Devices) and tap Refresh.
  • No log lines: the level is too high, or you just tapped Clear. Lower the level or wait.
  • Nothing matches the filter: the word is not in the lines that were read. Raise the number of lines or lower the level.

What density is, and why it matters on a watch

Density is measured in dpi (dots per inch). It is the number Android uses to decide how big to draw buttons, text and pictures. The screen itself has a fixed number of tiny dots. A lower density draws everything smaller, so more fits on the screen. A higher density draws everything larger and fits less.

On a small, round watch screen this is a big deal. At the maker's default, text can look huge and a list may show only two rows. Lowering the density by 20 or 40 can show a whole message at once. Raising it makes things easier to read and to tap. The sharpness does not change: only the size of things.

If the screen becomes unreadable

  1. Wait 15 seconds. The change undoes itself. The banner counts down on this phone.
  2. Or tap Put it back in the banner, or Reset to default (or Reset for the size).
  3. Or open the Console and run wm density reset and, if you changed the size, wm size reset. These work as long as the card says Connected, even when you cannot read the device's screen.
  4. If the connection is gone, connect again with + Add device (see Adding a device) and then use step 3.

The countdown runs in this app, on this phone. If you close the app, or the phone pauses it, or the connection drops during the 15 seconds, the automatic undo may not happen. That is why steps 2 to 4 exist. Switching to another device in the picker does not stop the undo: it still goes to the device that was changed.

This is a walk through for a Wear OS watch, from nothing to a managed watch: turn on developer mode, connect, then remove an app you never use, install an app, change the screen density, read the log and copy a file to this phone.

Before you start

  • A Wear OS watch (the examples are written for Wear OS 3 or newer) that is charged. Put it on its charger for this: debugging uses Wi-Fi, which drains the battery.
  • This phone, with this app, on the same Wi-Fi network as the watch. The watch itself must be joined to that Wi-Fi network, not only linked to the phone by Bluetooth.
  • About ten minutes. No working mode is needed on this phone for the Wi-Fi way.
Tip. Menu names on watches vary with the maker and the Wear OS version. If a name below is not exactly what you see, look for the nearest one: the idea is the same.

Part 1: turn on developer mode on the watch

  1. On the watch, open Settings.
  2. On most Wear OS watches go to System, then About, then Versions. On some it is About watch and the build is listed under software details. Where it sits varies, so look in Settings for About or System.
  3. Find Build number and tap it 7 times. A short message says that developer mode is on.
  4. Go back to Settings. A new entry, Developer options, is now there (on many watches inside System).

Part 2: turn on debugging

  1. Open Developer options. Turn on ADB debugging and confirm the question.
  2. Turn on Debug over Wi-Fi. The watch joins the Wi-Fi network if it has to, then shows an address with a port, such as 192.168.1.20:5555. Leave that screen reachable: you need the address.
  3. Check that this phone is on the same Wi-Fi network.

Part 3: pair and connect

  1. On the watch, under Debug over Wi-Fi, tap Pair new device. The watch shows a 6-digit code and a second address with another port, such as 192.168.1.20:37215. Do not close this screen.
  2. On this phone open the Connected Devices tab and tap + Add device. On the Wi-Fi tab type the pairing address in the first box and the code in Pairing code. Tap Pair. You read Successfully paired.
  3. Look at the watch's Debug over Wi-Fi address again (the first one, such as 192.168.1.20:5555). Type it into the second box and tap Connect.
  4. The sheet closes and the watch appears. If the watch asks Allow debugging?, tap Allow and tick Always allow.
  5. The card shows the watch's name, the badges Connected, Wi-Fi, Wear OS and Battery, and the seven sub-tabs.

Instead of typing, you can tap Nearby, then Scan the network: the watch shows up with Pair or Connect. If your watch has no pairing screen (some older ones), skip the pairing part and use Connect only. More about the sheet in Adding a device.

Example 1: remove a preinstalled app you never use

  1. Open the Apps sub-tab. The list reads from the watch. Tap 3rd Party or System to narrow it, or type a word in the search box.
  2. Find the app. If its name means nothing to you, leave it: use Debloater safety as a guide to what is safe.
  3. Tap Disable on its row. The row gets the DISABLED badge and the app is hidden from the watch's own app list.
  4. Use the watch for a few days. If anything breaks, tap Enable.
  5. If nothing broke and you want the space, tap the three dots, then Uninstall and confirm. A system app now shows UNINSTALLED; Reinstall brings it back.
Risky. Never remove the watch face, Settings, the Google or Wear OS services, the keyboard or the Bluetooth and phone-pairing apps. A watch that loses these may not work until it is factory reset, which erases it. When unsure, Disable, and only that.

Example 2: install an APK on the watch

  1. Have an APK built for Wear OS on this phone.
  2. Open the Send sub-tab and tap Choose package files. Pick the file.
  3. Tap Send to device. The bar moves and the row says Installed.
  4. Open the watch's app list. The app is there. If the row is red, read its message and see the table in Sending apps to the device.

Example 3: change the screen density

  1. Open the Display sub-tab.
  2. Tap − until the drop-down shows a value 20 to 40 lower than the one marked (default). Tap Apply selected.
  3. Look at the watch. Tap Keep within 15 seconds if you like it, or let it undo itself. Details: Screen density and size.

Example 4: read a log

  1. Open the Logcat sub-tab. Set the level to Error.
  2. Tap Clear, make the problem happen on the watch, tap Refresh.
  3. Read the red rows, or type the app's package name in the filter box. See The device's log.

Example 5: copy a screenshot or a file to this phone

  1. Open the Console sub-tab, tap Run after typing screencap -p /sdcard/screen.png.
  2. Open the Files sub-tab. Tap Storage, then screen.png, then Pull to this phone.
  3. Look in Download, ADB App Manager, Devices, then the watch's folder on this phone. Any other file works the same way, see The device's files.

The Bluetooth route, with no Wi-Fi

If the watch cannot use Wi-Fi, you can reach it over its Bluetooth link to this phone. It needs more things in place, and it is the least tested part of this tab.

  1. On the watch: Settings, Developer options, ADB debugging on, then Debug over Bluetooth on.
  2. In the Wear OS app on this phone: Watch settings, Advanced, Debugging over Bluetooth on.
  3. In this app, turn on ADB in a Working mode (ADB TCP or Wireless Debugging).
  4. In Connected Devices tap + Add device, open the Bluetooth tab, leave the port at 4444 and tap Connect over Bluetooth. Allow it on the watch if it asks.
Careful. This depends on the Wear OS companion app. It follows the method that is documented for Wear OS but has not been tried on every watch, so it may not work on yours. If it does not, use Wi-Fi.
